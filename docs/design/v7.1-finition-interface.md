## 2. Fonctionnement

### 2.1 Démarrage (console et journal)

```text
emu-rust.exe      (GUI)  ─┐
emu-rust-cli.exe  (CUI)  ─┴─► emu_app::run(Flavor)            Linux / macOS : le seul binaire `emu-rust`, Flavor::Console
run ─ LogBuffer::global() + couche de capture + sortie stderr (comme aujourd'hui)      ← avant toute autre chose
    ─ cli::parse
       erreur d'arguments, --help, --version, sous-commande :
            sortie standard présente (console du -cli, tube, fichier) ─► comme aujourd'hui (code de retour compris)
            Flavor::Gui sans sortie standard ─► fatal_dialog(« Ligne de commande : utilisez emu-rust-cli.exe »)
       mode fenêtre (bibliothèque, jeu) ─► prepare (racine, config)
            console_plan(flavor, sortie standard ?, config.interface.console, EMU_RUST_CONSOLE_CHILD) :
                 Relaunch ─► Command::new(<dossier de l'exe>/emu-rust-cli.exe).args(…).env(EMU_RUST_CONSOLE_CHILD, 1).spawn()
                             puis fin (code 0) ; échec ⇒ avertissement, on continue sans console
                 Stay     ─► LogBuffer::attach_file(<data>/logs/emu-rust.log)  (rotation .1, 2 Mio, crochet de panique)
                             ─► finish_pending_identities ─► emu_ui::run / run_library
       erreur fatale avant la fenêtre ─► journal + stderr + fatal_dialog (Windows sans sortie standard : MessageBoxW)
```

« Sortie standard présente » = poignée de `io::stdout()` ni nulle ni invalide (`AsRawHandle`, Rust sûr ; toujours
vrai hors Windows). Aucun appel de console : c'est Windows qui en donne une à `emu-rust-cli.exe`. Sous Linux /
macOS le réglage n'existe pas (ADR 0023 §3).

### 2.2 Rangement

```text
Réglages ─ « Créer les dossiers des systèmes » ─► create_system_folders(roms)                 (rien n'est déplacé)
         ─ « Ranger les ROMs… » ─► tâche de fond : Library::plan_tidy ─► TidyPlan
               écran d'aperçu : unités groupées par système de destination ;
                   Sûre (cochée) | Suggérée (décochée, raison) | Ambiguë (liste de systèmes, choix par unité ou
                   par extension) | Bloquée (raison) | Inconnue ; avertissement si un jeu connu change de système
                   total : N fichiers, X Mo, D dossiers créés ; [Ranger] [Annuler]
               [Ranger] ─► tâche de fond : Library::apply_tidy(plan, sélection)   (B ─ déplacement ─ base ─ C, par unité ; E)
                        ─► emu_runtime::relocate_identities(saves, report.moved)
                        ─► Library::mark_tidy_identities(journal)                  (ligne I)
                        ─► scan incrémental
                        ─► rapport : déplacés / laissés (raison) / échecs ; [Annuler ce rangement] [Ouvrir roms/]
         ─ « Annuler le dernier rangement » (si last_tidy() est annulable) ─► Library::undo_tidy ─► relocate_identities
               (liste nette du journal = report.moved, §3.4.1) ─► mark_tidy_identities ─► scan incrémental ─► rapport
ouverture de la bibliothèque, et lancement direct par la ligne de commande ─► finish_pending_identities :
      Library::recover_tidy (blocs B sans C défaits, E ou U posée) ─► pour chaque journal de pending_tidy_identities :
      relocate_identities(moved) ─► mark_tidy_identities            ─► puis scan au démarrage / lancement
```

`roms_root` est canonisé par `TidyOptions::new` ; tous les chemins absolus rendus (`TidyReport::moved`) en
dérivent. Le plan porte l'empreinte de l'état analysé (chemin, taille, date de chaque fichier d'une unité) :
`apply_tidy` revérifie chaque unité juste avant de la traiter ; une unité qui a changé depuis l'aperçu est laissée
(« modifiée depuis l'aperçu »). Le plan n'est jamais persisté.

#### 3.4.1 Journal de rangement : format 1, états, reprise, annulation (amendé après FV0, précisé après RV1, 2026-11-22)

Contrat de FB1b. Remplace la description de FB1a (`tidy/journal.rs`, à mettre à jour, en-tête de module compris).
**La version reste 1** : FB1a n'exécute rien, aucun journal n'existe chez l'utilisateur. Règles numérotées
« FV0 n » : rapport `.claude/fv0-7.1.md` (dépôt principal), à respecter en entier. Précisions « RV1 n » : revue
du présent paragraphe, rapport `.claude/rv1-7.1.md`, section « architecte » (I1 à I4 et mineurs).

**Grammaire.** Une ligne = un enregistrement terminé par `\n`, champs séparés par une espace.

```text
journal    = "emu-rust tidy 1" LF  "R " racine LF  [ aller [ annulation ] ]
aller      = { bloc }  [ "E" LF  [ "I" LF ] ]
annulation = { bloc }  [ "U" LF  [ "I" LF ] ]          ; seulement après le "E" (suivi ou non de "I")
bloc       = "B " u LF  { corps LF }  [ "C " u LF ]
corps      = "D+ " dossier | "D- " dossier | "S " dossier
           | "M " n " " taille " " mtime " " de " " vers | "m " n
           | "W " fichiers " " taille " " mtime " " de " " vers | "w"
```

- `u`, `n`, `fichiers` : `u32` ; `taille` : `u64` (octets) ; `mtime` : entier ≤ `i64::MAX`. Écriture décimale
  canonique : chiffres ASCII seuls, ni signe ni zéro en tête (sauf `0`). Chemins : inchangés (relatifs à la racine,
  `/`, `%XX`, composants contrôlés), plus M2 sous Windows.
- **`M <n> <taille> <mtime> <de> <vers>`** : taille et date du fichier source, lues par `symlink_metadata` au
  contrôle qui précède l'unité. **`W <fichiers> <taille> <mtime> <de> <vers>`** : agrégat du dossier, parcouru sans
  suivre de lien — nombre de fichiers ordinaires (récursif), somme de leurs tailles, plus récente de leurs dates
  (`0` sans fichier) ; les dates des dossiers eux-mêmes ne comptent pas.
- **`mtime`** = `scan::mtime_of` : secondes entières depuis le 1970-01-01 00:00:00 UTC de `Metadata::modified()`,
  fraction tronquée ; illisible ou antérieure à 1970 ⇒ `0`. Même valeur que `game.mtime_unix` et
  `Fingerprint::mtime`, sous Windows comme sous Unix. **« Même état que la ligne »** (seule comparaison permise
  entre le journal et le disque) : `taille` égale **et** `|mtime disque − mtime ligne| ≤ 2 s`
  (`MTIME_TOLERANCE_SECS` : grain de 2 s de FAT, arrondis des caches Windows et des partages réseau) ; pour `W`,
  les trois nombres (`fichiers` et `taille` exacts, date à 2 s près ; un lien ou un fichier spécial dans le dossier
  ⇒ différent). Un lien physique, un retrait de lien et un `rename` ne changent ni la taille ni la date : la
  tolérance ne sert qu'aux systèmes de fichiers à grain grossier. Le contrôle plan → exécution
  (`ChangedSincePlan`) reste exact. La date n'est **jamais** une preuve d'identité de deux fichiers (voir reprise).
- Un bloc s'ouvre à `B u` ; il est **validé** par `C u`, sinon **abandonné** (ouvert) à la ligne `B`, `E` ou `U`
  suivante ou à la fin du fichier. `n` repart de 0 dans chaque bloc.
- `D+` / `D-` / `S` / `M` / `W` sont des **intentions**, synchronisées avant l'opération (`create_dir`,
  `remove_dir`, création exclusive de l'assemblage, lien, `rename`) ; `m n` / `w` : lien `n` créé / `rename` fait
  (les sources d'un `M` sont retirées ensuite, sans ligne). `S <D>.emu-rust-part` : dossier d'assemblage de la
  destination `<D>` ; les `M … vers` et les `D+` d'un tel bloc nomment toujours le chemin **final** (sous `<D>/`),
  les liens étant créés à la même place sous le dossier `S`, renommé ensuite en `<D>` (sans ligne : le disque le
  dit).
- **`D+` : seulement pour un dossier que le bloc crée lui-même** (RV1 I4). La ligne est écrite à l'exécution,
  quand le bloc constate (`symlink_metadata`) que le dossier manque, juste avant son `create_dir` ; jamais d'après
  le plan : un dossier prévu au plan mais présent à l'exécution n'a pas de ligne. Un bloc à `S` peut ainsi écrire
  `D+` pour les **ancêtres** de `<D>` qu'il crée réellement (`roms/psx` absent), du moins profond au plus profond,
  avant sa ligne `S`.
- **Synchronisation** (RV1). Chaque ligne écrite est suivie d'un `sync_all` du journal avant de continuer : les
  intentions avant leur opération, et de même `m`, `w`, `C`, `E`, `U`, `I`. Le dossier **source** est synchronisé
  après le retrait des sources, avant `C`.
- Section d'annulation : le bloc `B u` d'une unité validée à l'aller porte ses déplacements **inversés** — même
  `n`, `de` et `vers` échangés, taille et date constatées à la destination au contrôle — sans `S` (retour par
  lien + retrait, ou `rename` pour `W`) ; `D+` = dossier recréé, `D-` = dossier créé à l'aller (ou `<D>`) retiré.

**Refus du journal entier** (`LibraryError::Journal`, numéro de ligne sans contenu ; rien n'est rejoué, pas même
l'ajout d'une clôture) pour toute ligne que la grammaire ne permet pas, et en particulier (FV0 2) :

1. `M`, `m`, `W`, `w`, `S`, `D±` hors d'un bloc ouvert ; `C u` ≠ `B u` ouvert ; `B u` déjà vu dans la section ;
2. `n` dupliqué dans un bloc (`M`) ; `m n` sans `M n` antérieur du bloc, ou répété ; `w` sans `W`, ou répété ;
3. plus d'un `S` ou d'un `W` par bloc ; `S` après un `M` ; `W` avec un `S` ou un `M` ; `S` dont le dernier
   composant ne finit pas par `.emu-rust-part` (ou s'y réduit) ; `M … vers` d'un bloc à `S` hors de `<D>/` ; `D+`
   d'un bloc à `S` qui n'est ni sous `<D>/` ni un ancêtre strict de `<D>` (RV1 I4) ;
4. `C u` alors qu'un `M` du bloc n'a pas son `m`, ou le `W` son `w` ;
5. section d'annulation : `S` ; `B u` sans `C u` à l'aller ; `M` / `W` qui ne sont pas l'inverse exact (mêmes `n`,
   chemins échangés, `taille` et `fichiers` égaux) de ceux du bloc `u` de l'aller ; un `M n` de l'aller sans inverse
   dans un bloc validé ;
6. quoi que ce soit après `U` hors un seul `I` ; `I` ailleurs que juste après `E` ou `U` ; second `E` ;
7. `M` ou `W` dont `de` et `vers` sont **égaux après pliage de casse et normalisation Unicode** (RV1 I1) : un
   déplacement qui ne change que la casse ou la forme Unicode désigne, sur un volume insensible à la casse, un
   seul fichier, que la branche « identiques ⇒ destination retirée » de la reprise détruirait. Le plan n'en
   produit pas ; l'écrivain n'en écrit pas ; le lecteur refuse le journal.

Invariant : **tout préfixe d'un journal valide coupé à une fin de ligne est un journal valide** (test : troncature à
chaque octet, FV0 15). Dernière ligne sans `\n` : ignorée à la lecture ; avant tout ajout, l'écrivain tronque au
dernier `\n` et synchronise (I1). **Fichier vide ou en-tête coupé** (moins de deux lignes complètes et contenu
préfixe de `emu-rust tidy 1\nR …`) : « rien n'a bougé » (FV0 11) — ni erreur ni journal ; `recover_tidy` le
supprime, les autres fonctions l'ignorent. Tout autre contenu non conforme : **illisible**.

**Création et bornes.** Le fichier est créé juste avant le premier `B` de l'aller (FV0 11 ; I4 : dossier
synchronisé) : un rangement qui ne commence aucune unité n'a pas de journal (`TidyReport::journal = None`). Nom :
`unix = max(maintenant, dernier + 1)` (M3) ; « le plus récent » = plus grand `(unix, k)`. Avant chaque bloc,
l'écrivain calcule la taille du bloc entier (`C` compris) : si le fichier dépasserait **7 Mio** (aller) ou
**16 Mio − 64 octets** (annulation), l'unité n'est pas commencée (laissée, signalée) et la section est close
(FV0 8, M1) ; l'annulation d'un aller ≤ 7 Mio tient donc toujours sous la borne de lecture.

**États** — un journal est **clos** si sa dernière ligne est `E`, `U` ou `I` (états 2, 3, 5, 6, lus sur cette
dernière ligne) ; sinon il est **en cours**, et c'est la **présence d'un `E`** qui distingue l'état 4 (annulation)
de l'état 1 (aller), pas la dernière ligne (RV1). `TidyJournalInfo` : `complete` = clos, `undone` = contient `U`,
`identities_done` = dernière ligne `I`, `moved` inchangé (déplacements validés de l'aller) :

| État | Forme | `complete` / `undone` / `identities_done` | Reprise (`recover_tidy`) | Identités (`pending_tidy_identities`) | Annulable |
|---|---|---|---|---|---|
| 0 vide / en-tête coupé | — | (pas un journal) | fichier supprimé | — | — |
| 1 aller en cours | pas de `E` | non / non / non | blocs ouverts de l'aller défaits, puis `E` ⇒ état 2 | — | non |
| 2 clos, identités dues | … `E` | oui / non / non | rien | liste nette | oui |
| 3 clos, identités posées | … `E` `I` | oui / non / oui | rien | — | oui |
| 4 annulation en cours | … `E` [`I`] `B` … sans `U` | non / non / non | blocs ouverts de l'annulation défaits, puis `U` ⇒ état 5 | — | non |
| 5 annulé, identités dues | … `U` | oui / oui / non | rien | liste nette | non |
| 6 annulé, identités posées | … `U` `I` | oui / oui / oui | rien | — | non |

Un marqueur de clôture (`E`, `U`) **ou** l'ouverture de la section d'annulation rend caduc le `I` antérieur : les
identités sont dues dès que la dernière ligne est `E` ou `U`, liste nette vide comprise (FV0 13). Un journal
illisible ou d'une autre racine n'a pas d'état : jamais rejoué, jamais complété, jamais purgé s'il n'est pas lisible.

**Liste nette** (`pending_tidy_identities`, du plus ancien journal au plus récent, racine courante seulement ; aussi
`TidyReport::moved` d'`apply_tidy`, `undo_tidy` et `recover_tidy`) : une paire absolue `(chemin périmé, chemin
actuel)` par déplacement des unités **validées à l'aller** — `(de, vers)` de l'aller si l'unité n'a pas de bloc
validé dans la section d'annulation, `(vers, de)` sinon ; fichier pour `M`, dossier pour `W` ; jamais les deux sens
pour un même fichier. Elle est correcte que le `I` de l'aller ait été posé ou non (une paire dont le chemin périmé
n'est dans aucun registre est sans effet) : c'est elle, et non les seules paires inversées, que l'UI passe à
`relocate_identities` après une annulation.

**`mark_tidy_identities`** (sous verrou) : relit le journal ; racine ≠ racine courante ⇒ `TidyRootMismatch` ;
dernière ligne `I` ⇒ `Ok` sans écrire ; dernière ligne ni `E` ni `U` ⇒ `TidyRefused(NotClosed)` ; chemin hors du
dossier des journaux ou fichier vide ⇒ `TidyRefused(UnknownJournal)` (RV3) ; sinon ajoute `I`, puis **purge**
(FV0 12) : au-delà des 20 plus récents, ne sont supprimés que les journaux lisibles dont la dernière ligne est `I`.
L'appelant ne l'invoque qu'après un `relocate_identities` `Ok` sur la liste nette de ce journal.

**Verrou et préalables** (FV0 3, 14). `apply_tidy`, `undo_tidy`, `recover_tidy`, `mark_tidy_identities` prennent
`try_lock` sur `journal_dir/lock` (`TidyBusy` sinon) pour toute leur durée. `apply_tidy` et `undo_tidy` refusent
tant qu'un journal du dossier est en cours (états 1, 4 : `TidyRefused(Interrupted)`) ou illisible (`Journal`) : la reprise, ou l'utilisateur
pour un fichier illisible, passe d'abord. La racine du journal est comparée à la racine courante **avant** toute
action, ajout de `E` / `U` / `I` compris. `recover_tidy` traite les journaux en cours de la racine courante (un seul
par construction ; sinon du plus ancien au plus récent, rapport cumulé), puis rend `Err(Journal)` s'il reste un
journal illisible, `Err(TidyRootMismatch)` s'il reste un journal en cours d'une autre racine — **sauf s'il a clos
au moins un journal** : alors `Ok(Some(report))`, les journaux restés bloquants dans `report.errors` (RV3,
§3.4.2) ;
`pending_tidy_identities` saute ces deux cas sans erreur.

**Exécution d'un bloc** (aller comme annulation ; FV0 4, 5, 7) : contrôles (`symlink_metadata` sur chaque
composant, source « même état » que le plan, destination libre) → `B`, `D+`, `S`, `M` / `W` synchronisés →
`create_dir` → liens (`m`) ou `rename` (`w`) → `sync_all` du dossier de destination (et `rename` de l'assemblage,
parent synchronisé) → retrait des sources, dossier source synchronisé → `D-` puis `remove_dir` des dossiers vidés
→ transaction `relocate` → `C u`. Un échec défait le bloc par la règle de reprise ci-dessous et passe à l'unité
suivante ; le bloc reste sans `C`. Jamais de `remove_dir_all` ; un dossier n'est retiré que par `remove_dir` (donc
vide).

**Échec de la défaite** (RV1 I2). Si la défaite d'un bloc échoue elle-même sur une erreur d'E/S (les cas « rien,
signalé » de la reprise n'en sont pas), l'exécution **s'arrête là** : aucune unité suivante, ni `E` ni `U`. Le
journal reste en cours (état 1 ou 4) et sera repris au démarrage suivant ; d'ici là il bloque tout rangement et
toute annulation (préalables ci-dessus). Même règle dans `recover_tidy` : il rend `Err` **sans poser de
clôture** ; la reprise, idempotente, recommencera.

**Reprise d'un bloc ouvert** (FV0 6, 7, 9 ; identique pour l'aller et pour l'annulation, où « source » = `de` de
la ligne inversée, c'est-à-dire l'emplacement rangé ; fondée sur le disque, idempotente ; tous les blocs ouverts de
la section en cours, du dernier au premier, lignes en ordre inverse) :

1. `D-` : dossier recréé s'il manque (`create_dir`) ;
2. chaque `M` — destination cherchée à `vers` puis, dans un bloc à `S`, à la même place sous le dossier `S` :
   - destination absente : rien ;
   - destination présente, source absente : retour à la source (lien + retrait) si la ligne a son `m` **ou** si la
     destination est dans le « même état que la ligne » ; sinon rien, signalé (fichier que le journal ne prouve pas
     avoir posé) ;
   - les deux présentes : **identiques** (même fichier physique prouvé par `same-file`, toute taille, plus les
     gardes de FV1a et de RV3 : §3.4.2 ; deux copies égales ne suffisent jamais, la borne de 512 Mio et le CRC32
     ne jouent plus) ⇒ destination retirée ; sinon rien, signalé. Le retrait exige en plus **`nlink ≥ 2`** sur la
     destination, relu juste avant (RV1 I1 ; sous Windows aussi depuis RV3) : un « même fichier physique » à un
     seul lien est un seul nom vu deux fois, on ne le retire pas (rien, signalé). Retrait refusé (« accès
     refusé ») : `TidyReport::extra_names`, non fatal (§3.4.2) ;
3. `W` : `vers` présent et `de` absent ⇒ `rename` inverse si `w` est écrit ou si le dossier est dans le « même état
   que la ligne » ; les deux présents ⇒ rien, signalé ;
4. nettoyage (RV1 I3), par `remove_dir` seulement : les `D+` **du plus profond au moins profond**, chacun cherché
   aux deux emplacements comme les `M` (à son chemin final et, dans un bloc à `S`, à la même place sous le
   dossier `S`) ; **puis** le dossier `S` ; **puis** `<D>`. Échec « non vide » : toléré et **silencieux** pour un
   `D+` (un dossier qui contient encore l'assemblage, ou un fichier venu d'ailleurs, reste), toléré et signalé
   pour `S` et `<D>` ;
5. base : réécriture inverse des fichiers revenus, une transaction, seulement si aucune ligne ne porte déjà la clé
   source (I5).

Puis la clôture de la section (`E` ou `U`). Une unité validée (`C`) n'est jamais retouchée par la reprise. Résultat
attendu sous pannes injectées à chaque appel système, annulation comprise (FV0 15) : aucun fichier perdu ni écrasé,
chaque unité entière d'un côté ou de l'autre.

**`undo_tidy`** (FV0 10). Le journal passé doit être **le plus récent** du dossier, lisible, de la racine courante,
en état 2 ou 3 ; sinon erreur (`Journal` / `TidyRootMismatch`) — un plus récent illisible bloque, on ne saute
jamais à un plus ancien. Un journal plus récent **d'une autre racine** bloque de même (`TidyRootMismatch` : le
plus sûr, on ne devine pas ce qu'il a déplacé) ; seul un fichier d'état 0 (vide, en-tête coupé) est ignoré pour
désigner « le plus récent » (RV1). Unités validées de l'aller, de la dernière à la première ; une unité revient si
**tous** ses `vers` sont présents, **sans lien** — ni lien symbolique (ou point d'analyse sous Windows), ni
fichier à `nlink > 1` (Unix ; Windows depuis RV3) —, sans attribut lecture seule (Windows, `ReadOnlyFile`), dans le « même état que la ligne » de l'aller, et si tous ses `de` sont libres
(dossiers parents manquants recréés, `D+`) ; sinon elle reste entière, dans `TidyReport::left`
(`ChangedSincePlan` ou `Conflict { existing }`). Après la dernière unité, ou à l'annulation entre deux unités
(`cancelled`), `U` est écrit : il n'y a **qu'une** section d'annulation, les unités restées rangées le restent.

**Annulation interrompue = définitive** (RV1). Une unité dont le retour a été coupé (état 4) est remise à son
emplacement rangé par la reprise, puis `U` est posé : elle ne pourra plus être annulée. Le rapport de reprise doit
le **dire** à l'utilisateur (texte de FU2b, à partir du `TidyReport` de `recover_tidy` et de
`TidyJournalInfo::undone`) : ces jeux restent rangés, à déplacer à la main si besoin.

**Limites et décisions après FV1a** (ADR 0023 §4.8, « Décisions après la revue FV1a »). (1) Retirer un exemplaire
« identique » exige `same_file::is_same_file` **et** `canonicalize(src) != canonicalize(dst)` ; plus de borne
512 Mio ni de CRC pour cette branche ; fichier non ouvrable : signalé, rien retiré. `same-file` devient dépendance
directe d'`emu-library` (licence à vérifier par l'implémenteur). (2) Windows : `sync_dir` sans effet (NTFS
acceptable) ; FAT / exFAT : renommage de dossier `W` ni atomique ni ordonné, limite assumée. (3) `fold_path` est
plus grossier que NFC (`é` == `e`) : refus ou `Conflict`, jamais fusion ; `Pokémon.gb` / `Pokemon.gb` vers le même
dossier restent non rangés, le message montre le fichier existant. (4) Fichier ouvert ailleurs (Windows) :
violation de partage = `Fatal`, journal en cours jusqu'à fermeture puis reprise ; l'UI l'explique. (5) Sur `Fatal`,
le `TidyReport` partiel est perdu : l'UI enchaîne `recover_tidy` puis `pending_tidy_identities`.

#### 3.4.2 Lecture seule, écriture refusée, ReFS, erreurs (revue RV3, 2026-11-23)

Contrat de **FB1d** (ADR 0023 §4.8, « Décisions après la revue RV3 » ; rapport `.claude/rv3-7.1.md`). Signatures
posées par l'architecte (`TidyBlock::{ReadOnlyFile, NotWritable}`, `TidySection`, `TidyExtraName`,
`TidyReport::{closed, extra_names}`, `LibraryError::TidyRefused`, `TidyRefusal`) ; rien ne les produit encore.

**1. Contrôle « lecture seule » (Windows).** Fonction privée `#[cfg(windows)]` : `symlink_metadata(p)
.permissions().readonly()`. Appelée sur chaque fichier que le bloc **retirera** : sources `M … de` à l'aller,
noms rangés `M … vers` à l'annulation (les `W` ne sont pas concernés : `rename` d'un dossier n'est pas gêné par
l'attribut de ses fichiers). Où : (a) dans `plan_tidy`, pour que l'aperçu montre `Blocked(ReadOnlyFile { path })`
(premier fichier trouvé, relatif à la racine) ; (b) au contrôle qui précède chaque bloc, **avant** `B` ; (c) dans
`undo_tidy`, avec les autres conditions de retour (unité laissée entière). Sous Unix : aucun contrôle (le retrait
dépend des droits du dossier : point 2). L'attribut n'est **jamais** modifié.

**2. Classement des refus d'écriture** (lien, `create_dir`, `rename`, création de l'assemblage — tous **avant**
le premier retrait de source, donc l'unité est défaite sans perte) :

| Erreur | Unix | Windows | Résultat |
|---|---|---|---|
| autre volume | `EXDEV` (`CrossesDevices`) | `ERROR_NOT_SAME_DEVICE` (17) (`CrossesDevices`) | `OtherVolume` |
| pas de liens physiques | `EPERM` (1) sur `link` | `ERROR_INVALID_FUNCTION` (1), `ERROR_NOT_SUPPORTED` (50) | `NoHardLinks` |
| écriture refusée | `EACCES` (13), `EROFS` (30, `ReadOnlyFilesystem`) | `ERROR_ACCESS_DENIED` (5), `ERROR_WRITE_PROTECT` (19) | `NotWritable { dir }` (parent de la cible) |
| fichier ouvert ailleurs | — | `ERROR_SHARING_VIOLATION` (32) | erreur d'E/S (`Fatal`, FV1a 4, inchangé) |
| destination prise | `EEXIST`, `ENOTEMPTY` | `ERROR_ALREADY_EXISTS` (183), `ERROR_FILE_EXISTS` (80) | `Conflict` |
| autre | | | erreur d'E/S de l'unité |

Codes lus par `raw_os_error()` (Rust confond `EPERM` et `EACCES` dans `PermissionDenied`) ; constantes locales,
pas de nouvelle dépendance ; macOS : mêmes valeurs Unix. Le lien d'un fichier en lecture seule est
en principe permis par NTFS (c'est son retrait qui échoue) : le point 1 ne compte pas sur ce tableau ; FB1d le
vérifie par le test `cfg(windows)`.

**3. Retrait refusé après le lien** (aller : `remove_file(source)` ; reprise et défaite : `remove_file(place)`
d'un nom prouvé second, branches `Identity::Same` et « retour par lien + retrait »). Si l'erreur est « accès
refusé » (`PermissionDenied`, ou `ERROR_ACCESS_DENIED` / `EACCES` / `EPERM` / `EROFS`) et que les deux noms sont
**prouvés** être le même fichier (relecture `identical` juste avant, ou lien posé par ce bloc et vérifié par
`is_same_file`) : **non fatal**. On pousse `TidyExtraName { remove, keep }` (`keep` = le nom que la base et le
journal désignent à la fin : la source pour une défaite, l'emplacement rangé pour une annulation défaite), on
continue la défaite et la section peut être close (`E` / `U`). À l'aller, l'unité est défaite (le lien posé est
le nom en trop si son retrait échoue aussi) et rendue dans `left` avec `ReadOnlyFile { path }` (attribut constaté
sous Windows) ou `NotWritable { dir }` (sinon). Toute autre erreur reste fatale (RV1 I2). Un nom laissé est
inoffensif pour les données ; le scan suivant peut le lister comme un jeu : l'UI le dit.

**4. Identité (`identical`), garde complète.** Dans l'ordre : deux `symlink_metadata` lisibles (sinon
`Unproven`) ; chemins pliés différents (`same_place`) et tailles égales à celle de la ligne ; **`links_of(dest) ≥
2`** — Unix `MetadataExt::nlink`, Windows `winapi_util::file::information(&Handle::from_path_any(dest)?)
.number_of_links()` (handle impossible ⇒ `Unproven`) ; `distinct_names` (canoniques distincts) ; **Windows** :
`created()` et `modified()` des deux noms **exactement** égaux (garde ReFS : index 64 bits non unique) ;
`same_file::is_same_file` ⇒ `Same` / `Different` / `Unproven`. `links_of` sert aussi au refus d'annuler un fichier
à plusieurs liens (Windows compris).

**5. Mineurs RV3.** Aller : `is_same_file(from, to)` doit être `Ok(true)` après le lien, avant `remove_file(from)`,
sinon `Step::Io`. `return_file`, branche `Identity::Same` : `self.sync_parent(source)?` avant
`remove_file(place)`. Tests de l'enregistreur (`Recorder`) : branche `Same`, `dir == linked.parent()`, total
contrôlé `> 0` en reprise.

**6. Erreurs.** `LibraryError::Journal` n'est plus rendu que pour un journal **illisible** (pas un fichier
ordinaire, plus de 16 Mio, hors grammaire, en-tête invalide) ; l'UI peut alors conseiller de déplacer le fichier
(il bloque tout). Correspondance des refus actuels :

| Aujourd'hui (`Journal`, message) | Désormais |
|---|---|
| « un rangement interrompu doit d'abord être repris » (`preflight`) | `TidyRefused { journal, reason: Interrupted }` |
| « aucun rangement à annuler » | `TidyRefused { reason: NothingToUndo }` (`journal` = chemin demandé) |
| « seul le dernier rangement peut être annulé » | `TidyRefused { reason: NotLatest }` |
| « ce rangement ne peut pas être annulé » (`undo_tidy`, état 5 / 6) | `TidyRefused { reason: AlreadyUndone }` |
| « rangement non terminé » (`mark`) | `TidyRefused { reason: NotClosed }` |
| « journal inconnu », « journal vide » (`mark`, `undo_tidy`) | `TidyRefused { reason: UnknownJournal }` |
| « écriture du journal interrompue », « chemin impossible à journaliser », « trop de journaux pour la même seconde », « racine non absolue ou non UTF-8 » (écriture), « journal vide » (`finish`, après écriture) | `LibraryError::Io { path, source: io::Error::other(message) }` |

**7. `recover_tidy`.** Pour chaque journal qu'il clôt, pousse `(chemin, TidySection::Tidy)` (état 1 → `E`) ou
`(chemin, TidySection::Undo)` (état 4 → `U` : annulation rendue définitive) dans `TidyReport::closed`. S'il a clos
au moins un journal, rend `Ok(Some(report))` même s'il reste un journal illisible ou d'une autre racine : ceux-ci
vont dans `report.errors` (chemin, message français de l'erreur qu'il aurait rendue) ; sinon, `Err` comme avant.
`apply_tidy` et `undo_tidy` laissent `closed` vide.

**Pour `ui` (FU2d).** (a) `text::block` : textes de `ReadOnlyFile` et `NotWritable` posés par l'architecte, à
relire ; (b) `error_text` : `Journal` = « illisible » + conseil de déplacer le fichier ; `TidyRefused` = texte
neutre de `reason` (jamais « supprimez ») ; `Io` = erreur d'écriture ; (c) « annulation interrompue rendue
définitive » déduite de `closed` (`TidySection::Undo`), plus de `last_tidy().undone` ni de
`INTERRUPTED_RECOVERED` générique quand `closed` est rempli ; (d) `extra_names` : section du rapport « Deux noms
du même fichier : retirez l'attribut « Lecture seule » de X (Propriétés), puis supprimez X ; Y est gardé » ;
« Annulation terminée » seulement si `errors` **et** `extra_names` sont vides ; (e) texte sélectionnable /
« Copier » (demande utilisateur) s'applique aussi à ces messages.

## 7. Risques

| Risque | Parade |
|---|---|
| Perte ou mélange de fichiers de l'utilisateur | liens physiques et `create_dir` exclusif (jamais d'écrasement) ; journal avant action ; unité indivisible, défaite à la reprise ; annulation ; revue du journal avant l'exécution ; pannes injectées à chaque primitive |
| `.srm` attribué à un autre jeu après rangement | `relocate_identities` obligatoire, marqueur `I`, rejoué à chaque ouverture et avant un lancement direct ; chemins canoniques |
| Console : relance qui boucle ou voisin absent | variable `EMU_RUST_CONSOLE_CHILD`, décision pure testée, repli sans console |
| `rc.exe` absent (compilation croisée) | `build.rs` sans ressource, avertissement, jamais d'échec |
| Rendu SVG différent selon l'outil | fichiers générés commités ; la CI ne compare que l'empreinte du SVG |
| États sauvegardés qui mémorisent le chemin du média | mesuré par FQ3 ; documenté ; l'annulation remet les chemins |
| Analyse lente (gros CD, hachage) | empreintes reprises de la base ; mêmes bornes que le scan ; annulable |
| Jeu-dossier DOS pris à tort (dossier Windows quelconque) | statut « Suggérée », décoché d'office, jamais éclaté |
| Rangement refusé chez un utilisateur (autre volume, exFAT, `roms/<id>` lié) | blocage expliqué dans l'aperçu ; limite assumée de la 7.1, à rouvrir si l'essai le demande |
| Seconde instance en train de jouer pendant un rangement | non exclue (limite de l'ADR) ; dite dans l'écran d'aperçu et le guide d'essai |

### 10.1 Résultats de FX0 (2026-11-21)

1. **Classeur** : réutilisable sans duplication. `analyze` (et `analyze_file`) prend un `Found` dont `folders`
   porte la règle de dossier : `folders = []` la neutralise et rend `Rule::Identify { candidates }`, `ByDat`,
   `Disc`, `Dos` ou `Playlist`. Résolution : `resolve` → `identify` / `dat_match` (`db.rs`) ne fait que des
   `SELECT` (cache `NameIndex`) : utilisable en lecture seule ; `store` / `store_batch` écrivent, à ne pas
   appeler. **Écart** : pour une extension réservée au dossier (`.chd`, `.cue`, `.iso`, `.m3u`… hors de
   `roms/<id>/`), `attribute` rend `Unclassified` (⇒ `Failure::Unclassified`) : les **candidats** d'une unité
   ambiguë viennent de `systems_for_extension` (qui inclut les systèmes à `folder_extensions`), pas du `Rule`.
   `audio_track_name` est pur ; `hide_disc_tracks` prend `&[Found]` + un `ScanReport` de brouillon : partageables
   tels quels ; `normalize_root`, `Found`, `Analysis`, `Rule`, `analyze`, `lower_ext`, `entries_have_executable`
   passent en `pub(crate)` (FB1a). Le cache `PROBES` (thread-local) doit être vidé au début de `plan_tidy` comme
   dans `run`. Le parcours `Walk` n'est **pas** réutilisable tel quel : il suit les liens de fichier (le rangement

   `fs::canonicalize` ajoute `\\?\`, ailleurs une racine liée diffère). `TidyOptions` garde donc aussi, en privé,
