## 2. Scan (`emu-library`)

Le 7z stocke un CRC32 par fichier dans l'en-tête, lisible **sans décompresser** (l'en-tête seul est lu ; il est
lui-même LZMA-compressé mais petit). Stratégie à deux niveaux, ADR 0014/0005 :

- **Avant ouverture** (lecteur commun, aussi pour le lancement) : taille du fichier d'archive ≤
  `MAX_ARCHIVE_FILE_BYTES` (proposé : **4 Gio**, valeur confirmée au lot T1 ; revue en 8.1.1 pour les gros CD) et,
  lue dans l'en-tête de départ de 32 octets, taille de l'en-tête suivant ≤ `MAX_7Z_HEADER_BYTES` (proposé :
  **16 Mio**) et son décalage dans le fichier ; sinon archive refusée (scan : non identifiée ; lancement :
  `TooLarge`). Ensuite `read_with_memory_limit` (64 Mo). **Lot T1** : lire dans le code de `sevenz-rust2` 0.27.0
  ce que cette borne couvre — en-tête compressé (taille décodée de l'en-tête), nombre de fichiers et de dossiers
  annoncé (allocations proportionnelles), mémoire PPMd (`order` / `mem_size`), dictionnaire LZMA / LZMA2 — et
  écrire le résultat ici ; ce qui n'est pas couvert est contrôlé par emu-rust sur les propriétés des codeurs de
  chaque dossier **avant** tout décodage (même borne de 64 Mo), cas ajoutés au fuzz (T5b).
- Lister les entrées (nom, taille, CRC32, dossier / lien / anti-item, chiffrement) : identification par
  **CRC32 + taille** contre le DAT / libretro-database (qui indexe déjà CRC32 ; sinon retomber sur SHA1).
- **Liens** : une entrée dont les attributs portent le drapeau d'extension Unix (`0x8000`) et `S_IFLNK`
  (`0o120000`) dans les 16 bits hauts (`(attr >> 16) & 0o170000 == 0o120000`), ou le drapeau Windows de point de
  réparation (`0x400`), est un lien : `is_file = false`, jamais extraite.
- **Chiffrement** : un en-tête chiffré rend le listing impossible (`ListError::Encrypted`) ; des données chiffrées
  sous un en-tête lisible donnent `encrypted = true` pour chaque entrée d'un dossier dont un codeur est AES
  (`06F10701`). Dans les deux cas : scan ⇒ archive **non identifiée** (aucun jeu, raison au rapport de scan) ;
  rangement ⇒ unité **inconnue** ; lancement ⇒ `ArchiveError::Encrypted`. Jamais de demande de mot de passe.
- **Volumes** `.7z.001`, `.7z.002`… : non pris en charge ; ignorés au scan (extension `001`… inconnue), comme
  aujourd'hui.
- SHA1 seulement si l'identification CRC32 + taille échoue ou si le DAT n'a que SHA1 : décompression d'une seule
  entrée, bornée (`max` existant, annulation par `cancel`), jamais pour toute l'archive solide si évitable.
- CRC absent (entrée sans CRC) : décompression bornée de cette entrée ; archive solide : une seule passe
  séquentielle, entrées inutiles jetées (le solide impose de décoder le bloc jusqu'à l'entrée).
- Bornes : nombre d'entrées (comme zip), taille déclarée par entrée et totale, bloc solide ≤ 512 Mio décodés au
  scan (constante `MAX_SCAN_DECODE`, §9.1), dictionnaire déclaré ≤ 64 Mo.
- **CD dans une archive** : toujours refusé au scan en 8.1 (`ZIPPED_DISC` gardé, aussi pour un `.7z`) ; 8.1.1 : §9.3.
- Mêmes règles que `analyze_zip` (`zip_disk_order`, sonde `.bin` et 32X, regroupement des disquettes).
  Refactor : un lecteur commun (`ArchiveReader`, listing `ArchiveEntryInfo { name, size, crc32: Option<u32>,
  is_file, encrypted }` ; `encrypted` toujours `false` pour un zip non chiffré, un zip chiffré garde son refus
  actuel) pour que `analyze_zip` devienne `analyze_archive` sans dupliquer la logique. `zip_media_agrees` et
  la colonne `media` acceptent un `.7z` (nom gardé).
- **Systèmes personnalisés** : un `.7z` sous `roms/<id>/` dont une entrée a une extension du système est un jeu de
  ce système (règle du zip, ADR 0025 §9 « Archives ») ; hors de ce dossier, attribution inchangée (ADR 0025 §12).
- Le scan ne remplit PAS de cache d'extraction (coût disque inutile).

## 3. Lancement (`emu-runtime`)

Même chemin que le zip, aux mêmes conditions, sauf ce qui suit :

- **Cartouche** (`content.rs`, `prepare`) : un `.7z` est transmis tel quel **seulement** si le core liste `7z`
  dans `valid_extensions` ; `block_extract` ne vaut **pas** pour le `.7z` (il garde son effet pour le zip). Sinon
  la première entrée acceptée est extraite en mémoire (`GameSource::Memory`) ou, si `need_fullpath`, dans le
  dossier temporaire privé (pas de copie persistante : réextraite à chaque lancement, comme le zip).
- **DOS** (décision de l'utilisateur, 2026-11-27) : `dosbox_pure` reçoit le `.7z` **tel quel** s'il liste `7z`
  dans `valid_extensions` (le `.info` connu ne le liste pas, ADR 0018 : `zip|dosz|…`) ; sinon le lancement est
  refusé avant tout chargement, refus de lancement nouveau (`LaunchRefusal::SevenZipDos`, nom définitif au lot
  T1) au texte « Ce core DOS ne lit pas les `.7z` : convertissez l'archive en `.zip` ». **Jamais d'extraction
  partielle** d'un jeu DOS (une arborescence partielle donnerait un jeu cassé).
- **Disquettes** (`media.rs`, `zip_images` → `archive_images`) : listing par en-tête, filtré par
  `zip_entry_accepted` (`workcopy.rs`) ; liens (§2), dossiers, `..`, chemins absolus, noms à NUL et entrées
  chiffrées ignorés ; extraction par `workcopy.rs` dans la copie de travail (`<saves>/<core>/<jeu>.disks/`), nom
  de fichier = nom de base assaini, jamais le chemin de l'archive (zip-slip impossible). Ordre d'évaluation du
  design 3.0 §3.5.1 inchangé : un `.7z` qui contient des images acceptées est extrait même si le core lit le `.7z`.
- Archive solide : décodée séquentiellement **une seule fois** pour toutes les entrées voulues (multi-disques : une
  passe, pas N). Le CRC32 stocké est revérifié à l'écriture ; échec = erreur, copie supprimée.
- **Bornes absolues seulement** (pas de ratio de compression) : taille du fichier d'archive et de son en-tête avant
  ouverture (§2) ; taille **déclarée** par entrée (`Limits`) et totale (`MAX_COPY_BYTES`, 2 Go) contrôlées avant
  de décoder ; en cours de flux, **arrêt dès que les octets décodés d'une entrée dépassent sa taille déclarée**
  (`ArchiveError::Corrupt`) ; dictionnaire et mémoire des codeurs (`read_with_memory_limit` 64 Mo et contrôles du
  §2) ; **traversée d'un dossier solide** bornée : octets décodés jusqu'à la dernière entrée voulue (entrées
  sautées comprises) ≤ `MAX_COPY_BYTES`, contrôlé sur les tailles déclarées avant de décoder puis en cours de flux
  (comme `MAX_SCAN_DECODE` au scan) ; annulation coopérative.
- **Écriture** : chaque copie passe par `write_atomic_with` (`saves.rs`, `pub(crate)` dans `emu-runtime`) :
  temporaire `.<nom>.tmp-<pid>` dans le même dossier, `sync_all`, renommage, temporaire supprimé en cas d'erreur
  (CRC faux, annulation, disque plein, corruption). **Pas de `.partial`, pas d'étape de nettoyage au démarrage.**
  Un arrêt brutal pendant l'extraction peut laisser un temporaire : remplacé par une écriture ultérieure du même
  nom et du même pid, sinon laissé ; son dossier n'est alors plus « intact » (§3.1) et n'est jamais évincé
  (limite acceptée, coût disque borné par la taille d'une entrée).
- **Place libre** : **pas de vérification préalable** (aucune crate, aucun `unsafe`). Un disque plein pendant
  l'écriture (`io::ErrorKind::StorageFull` ou `QuotaExceeded`, correspondance Windows à vérifier au lot T3) donne
  `ArchiveError::DiskFull` : « Disque plein pendant l'extraction de (archive) : libérez de la place puis
  relancez » ; temporaire supprimé, aucune copie partielle gardée.
- **Cache** : la copie de travail est déjà persistante (sauvegardes, disquettes ; `MAX_WORK_DIRS` = 64,
  `media.rs` / `identity.rs`) ; pas de second cache. Ajouté : plafond total (`[library] archive_cache_mb`, défaut
  **2000**, minimum **1000**, §9.4) et éviction LRU (§3.1).
- Progression : `Progress { done_bytes, total_bytes, entry }` via un rappel `FnMut` (modèle `Limits` / `cancel`),
  affichée par l'UI (barre + bouton Annuler) dès qu'une extraction dépasse une seconde ; un solide LZMA2 de 200 Mo
  dure ~20-40 s sur le Mac de test ; l'extraction tourne hors du thread de l'interface.

### 3.1 Plafond et éviction LRU (décision de l'utilisateur du 2026-11-27)

À relire par `reviewer` **opus** (suppression de données de l'utilisateur) **avant** l'implémentation de T3, puis
au lot T6. Amendé après la relecture tour 2 (format du manifeste, verrou d'usage).

- **Mesure** : plafond **commun à tous les cores** (un seul réglage, comme le dit l'interface : « place maximale
  des copies de travail ») ; somme des tailles des fichiers de tous les dossiers `<saves>/<core>/*.disks`, tous
  cores et toutes origines confondus, sans suivre les liens, calculée avant une extraction de disquettes `.7z`.
  Total + taille déclarée à extraire ≤ plafond : rien à faire.
- **Manifeste** (`.emu-rust-disks`, `workcopy.rs`) — deux formats, choisi **à chaque écriture** :
  - **v1 inchangé, octet pour octet** (`emu-rust working copies 1`, 7 champs par entrée) pour tout dossier dont
    **au moins une** entrée n'a pas l'origine `.7z` : dossier issu d'un `.zip`, mixte (disque ajouté du menu),
    ou créé par une 7.x / 8.0. Ni champ nouveau ni `last_used` : une 7.6 ou une 8.0 qui le relit le lit à
    l'identique (sinon elle le classerait `Unreadable`, ouvrirait un dossier `(n).disks` neuf et réextrairait :
    progression perdue en apparence). Un dossier `.7z` auquel on ajoute un disque d'une autre origine repasse
    en v1 (marques `.7z` perdues : il n'est plus jamais évinçable, ce qui est voulu).
  - **v2** (`emu-rust working copies 2`, contenu exact fixé au lot T1) **seulement** si **toutes** les entrées ont
    l'origine `.7z`. Champs ajoutés par entrée : `seven_zip` (champ **à part** : `Origin` garde son sens actuel
    `Set` / `Added`), `entry_size` et `entry_crc32` (taille déclarée et CRC32 de l'**entrée** lus dans l'en-tête
    du `.7z`, distincts de `size` / `crc` qui identifient la **source**) ; par dossier : `last_used` et `game`
    (nom assaini du jeu, qui désigne le verrou). Une 8.0 le
    classe `Unreadable` et le laisse tranquille ; elle ne sait de toute façon pas extraire un `.7z`.
- **Verrou d'usage** (choix : un verrou **par nom de jeu**, pas un verrou global) :
  `<saves>/<core>/.<jeu>.disks.lock` (nom de jeu assaini comme `work_dir_for`), **hors** du dossier de copies,
  couvrant `<jeu>.disks` et tous les `<jeu> (n).disks`, **jamais supprimé** (fichier vide ; ni l'évinceur ni le
  lanceur ne le retirent, une suppression ouvrirait une course entre deux instances).
  - **Lanceur** : prend le verrou **partagé** (`File::lock_shared`) **avant** `inspect` / `prepare` et le garde
    toute la session de jeu, y compris pendant l'extraction et l'essai à blanc (§3.2). Deux instances du même jeu
    l'obtiennent toutes deux : comportement actuel conservé (`media.rs`, `choose_dir` au `e3c1de0` ~l.527 :
    « Two instances of the very same game starting together can still share a folder (not guarded) »).
  - **Lanceur qui n'obtient pas le verrou** (seul cas : une éviction de ce jeu est en cours, verrou exclusif) :
    nouvel essai non bloquant (`try_lock_shared`) toutes les 100 ms pendant au plus 10 s (une éviction ne
    supprime que quelques fichiers), puis refus du lancement « copies de travail de (jeu) en cours de nettoyage :
    relancez » (`RuntimeError` du lancement, pas d'`ArchiveError`). Un verrou impossible à créer (droits,
    disque) : lancement **sans** verrou, avertissement au Journal, **seulement** depuis un dossier v1 (jamais
    évincé) ; si le dossier du jeu est en v2, les disquettes sont extraites dans le dossier temporaire privé
    (écritures perdues à la sortie, dit à l'utilisateur), jamais de lancement depuis un dossier v2 sans verrou.
  - **Évinceur** : tire le nom du verrou du champ `game` du manifeste v2 (nom assaini du jeu), **jamais** du nom
    du dossier, ambigu (`Foo (2).disks` = jeu « Foo (2) » ou 2e dossier de « Foo », `work_dir_candidate`,
    `media.rs` ~l.216-221) ; dossier v2 sans ce champ ⇒ jamais évincé. Il prend le verrou **exclusif** sans
    attendre (`try_lock`) ; refusé, ou fichier verrou impossible à ouvrir ou à créer ⇒ dossier gardé. Il garde
    le verrou pendant la vérification **et** la suppression.
  - Justification contre un verrou d'éviction global : il ne dit pas quel jeu est en cours dans quelle instance
    (il faudrait en plus un registre des jeux ouverts) et sérialiserait tous les lancements de toutes les
    instances pendant une éviction ; le verrou par jeu est local, sans état partagé, et suit la règle actuelle
    de deux instances.
  - **Windows** : `File::lock*` = `LockFileEx` (verrou obligatoire sur le fichier verrou seulement) ; le fichier
    verrou n'est jamais supprimé, donc `FILE_SHARE_DELETE` ne le concerne pas. Côté copies : une copie encore
    ouverte par un autre programme (antivirus, indexeur) fait échouer `remove_file`, ou la laisse en « suppression
    en attente » ; `remove_dir` échoue alors (dossier non vide). Traitement : arrêt de l'éviction de ce dossier,
    avertissement au Journal, nouvel essai à la prochaine éviction.
- **Évinçable** = toutes ces conditions, vérifiées sous le verrou exclusif au moment de l'éviction :
  1. dossier avec manifeste lisible en **v2** (`DirState::Manifest`), **jamais** `Legacy`, `Unreadable`,
     `NotDir` ni un manifeste v1 ;
  2. **chaque** entrée a `seven_zip` (garanti par le format v2, revérifié) et le champ `game` est présent ;
  3. chaque copie du manifeste est présente, fichier ordinaire (pas un lien), de taille égale à `entry_size` et de
     CRC32 égal à `entry_crc32` (relu en entier : une écriture du core, même de taille identique, change le CRC) ;
  4. aucun autre fichier ni sous-dossier que le manifeste et le `.m3u` généré par emu-rust, de nom exact
     `<jeu>.m3u` (nom assaini du jeu, comme `choose_dir`) : un temporaire orphelin, un fichier de sauvegarde du
     core, un autre `.m3u`, un dossier inconnu ⇒ gardé ;
  5. le jeu en cours de cette instance est exclu aussi par son chemin (en plus du verrou).
- **Ordre LRU** : `last_used` (secondes UTC) du manifeste v2, réécrit à chaque lancement qui utilise le dossier ;
  absent ⇒ date de modification du manifeste. Jamais `atime` (désactivé ou différé selon les montages, peu fiable
  sous Windows). Les plus anciens d'abord, jusqu'à repasser sous le plafond.
- **Suppression** : manifeste relu juste avant ; suppression fichier par fichier des seuls noms attendus (copies du
  manifeste, `<jeu>.m3u`, manifeste **en dernier**), par `symlink_metadata` et `remove_file` (un lien est retiré
  lui-même, jamais sa cible ; jamais `remove_dir_all`), puis `remove_dir` du dossier vide. Un échec à n'importe
  quelle étape arrête l'éviction de ce dossier sans erreur pour le lancement (avertissement au Journal). Arrêt
  brutal en cours : le manifeste reste avec des copies manquantes ; le dossier n'est plus évinçable (condition 3)
  et le lancement suivant recrée les copies absentes depuis le `.7z`.
- **Plafond impossible à tenir** (copies non évinçables trop grosses) : l'extraction a lieu quand même,
  avertissement au Journal « plafond du cache dépassé : N Mo de copies gardées (écritures ou anciennes versions) ».
  Choix technique tranché (réversible) : refuser le lancement priverait l'utilisateur d'un jeu à cause de copies
  qu'il ne peut pas voir dans l'interface.
- L'éviction n'est jamais écrite au journal de rangement et ne touche jamais `roms/` ni les sauvegardes (SRAM,
  états), qui ne sont pas dans les dossiers `.disks`. **Lot T3** : vérifier qu'aucune sauvegarde d'état ni
  identité (`identity.rs`, registre) ne dépend du chemin `<jeu> (n).disks` d'une copie évincée puis recréée sous
  un autre `n`.

**Pour plus tard** (mineurs de la relecture tour 3, non traités ici ; à reprendre au lot T1 ou T3) :

- fichiers `.lock` cachés ignorés par tout code qui liste `<saves>/<core>/` (T3) ;
- réessai de 10 s du lanceur hors du thread de l'interface, avec « Annuler » ;
- `last_used` écrit par deux instances : l'écriture atomique suffit (à confirmer) ;
- avertissement « plafond dépassé » une seule fois par session ;
- tests : 2e instance sur un dossier v2 sans verrou ; jeu nommé « Foo (2) ».

### 3.2 Garde-fous de la 8.0 (ADR 0025 §5) face à un `.7z`

- **Témoin de lancement** (`launch-<pid>.marker`) : créé **après** l'extraction réussie, juste avant `load_game`.
  Une extraction longue, annulée ou en erreur n'est jamais prise pour un plantage du core au démarrage suivant.
- **Enfant `--dry-run-child`** (essai à blanc d'un core non testé) : à fixer au lot T1, avec cette
  **recommandation** : le parent extrait d'abord (barre de progression, annulation, plafond, dans la vraie copie de
  travail ou le dossier temporaire, comme le lancement qui suit) ; l'enfant reçoit le contenu **déjà extrait**,
  copié dans son dossier d'essai selon la règle des 256 Mio d'ADR 0025 §5 ; l'enfant ne décode jamais de `.7z`
  (aucun LZMA dans le processus de garde, et le délai de 30 s ne mesure que le core). Le parent tient le verrou
  par jeu (§3.1) en partagé de l'extraction à la fin de la session, essai à blanc compris. Si le core liste `7z`, le
  `.7z` est copié tel quel (règle des 256 Mio). Le lot T1 vérifie que l'enfant de PB3 / PB4 permet cette
  requête et écrit la règle dans l'amendement d'ADR 0025 §5 si elle change le contrat.

## 4. Multi-disques, CD, m3u

- Disquettes (Amiga, CPC, C64, Atari ST…) : même logique que zip (`zip_disk_order`, ≤ 32 images).
- m3u dans le 7z : ignoré comme pour zip ; m3u externe référençant un `.7z` : supporté via le même résolveur.
- `.7z` contenant un `.zip` ou un autre `.7z` : archive sans image acceptée (pas d'archive imbriquée).
- **CD** (cue + bin, iso) dans un `.zip` ou un `.7z` : **refusé en 8.1** avec le message actuel (« décompressez ou
  convertissez en CHD »). L'extraction proposée (décision de l'utilisateur du 2026-11-24, fin du document) est
  repoussée en **8.1.1** (grill T1-4), détaillée au §9.3.

## 5. Cores qui lisent le 7z eux-mêmes

puae, VICE (`block_extract = true`) : ADR 0017/0019 ont choisi « le frontend extrait, le core reçoit des images »
pour garder les écritures. Même règle : une archive `.7z` contenant des images acceptées est extraite par le
frontend (ordre d'évaluation du design 3.0 §3.5.1) ; sans image acceptée, transmise telle quelle seulement si le
core liste `7z` dans `valid_extensions` (`block_extract` ne compte pas pour le `.7z`, §3). Les tables des ADR 0017
(l.314, « `.7z` et CD hors bibliothèque »), 0018 (DOS, §3) et 0019 (l.82, `block_extract` : extraction de VICE dans
`<saves>/TEMP`, écritures perdues) sont mises à jour par le lot T1 (pas de nouvelle ADR : renvoi vers 0027).

## 6. Autres usages du zip

- `emu-assets/src/cores/archive.rs` : les cores du buildbot sont en `.zip` ; le 7z n'y est PAS ajouté (surface
  d'attaque réseau inutile). Les BIOS libres idem.
- `emu-ui/src/launch_firmware.rs` : `zip_entry_extensions` → lire aussi les entrées d'un `.7z` (listing d'en-tête).
  API : un seul `emu_library::archive::list_extensions(path)`, utilisé par le scan, le rangement et le bandeau de
  fichiers d'origine (trois implémentations évitées) ; `emu-ui` n'a pas de dépendance à `sevenz-rust2`.
- Placement : la lecture d'archive vit dans `emu-library` (listing + CRC, nouveau `src/archive.rs`) ;
  `emu-runtime` ne peut pas en dépendre (graphe) → l'extraction a sa propre dépendance `sevenz-rust2` dans
  `emu-runtime` (déjà le cas de `zip`) ; `emu-ui` appelle `emu-library`. Pas de nouveau crate, pas de changement
  de graphe.

### 9.1 Rangement des ROMs (ADR 0023 §4)

- **Unité** : un `.7z` est un « fichier seul » (ligne `.zip` de §4.2), déplacé tel quel vers `roms/<id>/<nom>`.
  Le rangement ne décompresse jamais (§4.1) : rien ne change pour lui, sauf le listing.
- **Système de destination** (§4.3 étape 3, « contenu de l'archive ») : extensions des entrées lues par
  `emu_library::archive::list_extensions` (en-tête seul, §6), résolues contre l'instantané du catalogue du plan ;
  pas de second lecteur dans `tidy`. Un `.7z` chiffré (en-tête chiffré, ou une entrée `encrypted`) ou illisible
(bornes du §2 comprises) : unité **inconnue**, laissée en place. Un
  système personnalisé n'est candidat que dans les conditions d'ADR 0025 §12 (extension propre, « Suggérée »).
- **CD archivé** (grill Z1, T1-1) : la sonde d'en-tête de piste (étape 1) demanderait une décompression ; elle n'est
  pas faite. À la place : les CRC32 + tailles des pistes **`.bin`** (le `.cue`, texte réécrit d'un dump à l'autre,
  est **ignoré** ; une `.iso` seule compte comme une piste), lus dans l'en-tête, sont cherchés dans les DAT (Redump)
  des systèmes à disque candidats (megacd, psx, 3do) ; toutes les pistes d'un même jeu d'un seul système ⇒
  « **Sûre** » (raison DAT) ; sinon le nom exact de l'archive (sans extension) égal au nom d'un jeu du DAT d'un seul
  système ⇒ « **Sûre** » ; sinon « **ambiguë** » entre les systèmes qui acceptent les extensions trouvées ;
  jamais « Sûre » par extension seule. Cette règle **remplace** `TidyBlock::DiscInArchive` (`tidy/plan.rs`), pour
  le `.zip` comme pour le `.7z` (le CRC est aussi dans le répertoire central du zip) (confirmé par
  l'utilisateur le 2026-11-27). Le CD rangé reste refusé au scan et au lancement jusqu'à la 8.1.1. Le texte de
  l'interface (`emu-ui/src/library/tidy/text.rs:180` au `e3c1de0`, « image de CD dans une archive : non prise en
  charge ») change avec le lot T4. **Amendement d'ADR 0023 §4.3** (~l.391, étape 3 « une image CD dans un zip
  reste refusée ») et exception « nom exact ⇒ Sûre » pour un CD archivé : écrits au **lot T1**, pas avant.
- **Collisions** (§4.4) : taille et CRC32 du fichier `.7z` entier, comme un zip. Aucune règle nouvelle.
- **Copies extraites** : la copie de travail est indexée par l'identité de la source (`ManifestEntry`) ; l'étape (5)
  `relocate_identities` (`emu-runtime/src/identity.rs`) la réécrit pour un `.7z` comme pour un zip, à l'aller et à
  l'annulation. Le cache extrait et les sauvegardes suivent donc le jeu rangé ou ramené.
- **Journal inchangé** : le rangement ordinaire écrit la version 1, la bascule avec déplacement (8.0) la version 2
  (ADR 0023, amendement du 2026-11-27) ; un `.7z` y est un « fichier seul » sans ligne nouvelle ; l'éviction LRU
  n'est jamais écrite au journal (elle ne touche pas `roms/`).
- **Exclusion** : une extraction de lancement est une tâche de fond au même titre qu'un scan ; le rangement est
  refusé pendant une extraction, et un lancement qui doit extraire est refusé pendant un rangement (message « tâche
  en cours »).
- **Démarrage** (ADR 0025 §13) : **inchangé** ; plus d'étape de nettoyage des `.partial` (écriture par
  `write_atomic_with`, §3).
- **Unités** de taille : bornes et plafond en octets dans le code, affichés en Mo / Go décimaux comme le reste de
  l'interface (« ≈ 680 Mo ») ; la borne de scan de 512 Mo décompressés reste alignée sur la borne CRC Mega CD de
  **512 Mio** (D8) : même constante `MAX_SCAN_DECODE = 512 * 1024 * 1024`.

**Décision de l'utilisateur (2026-11-27)** : la règle « Sûre si reconnu, sinon ambiguë » s'applique aussi aux CD
dans un `.zip` (aujourd'hui « bloqué : CD dans une archive ») : même règle pour les deux formats.

### 9.2 Schéma v8

Aucune migration : la base reste en **v8** (`game.scan_pending` de la 8.0, `needs_32x` de la 7.4). `media` et
`zip_media_agrees` acceptent un chemin `.7z` sans colonne nouvelle (le nom `zip_media_agrees` est gardé). Une base

### 9.3 CD archivés et CD 32X — **8.1.1** (hors 8.1)

En 8.1 : `ZIPPED_DISC` et `LaunchRefusal::ArchivedDisc` sont **gardés** (le second couvre aussi le `.7z`) ;
aucune ligne de jeu pour un CD archivé ; `Library::set_needs_32x` n'est pas posée. Ce qui suit est la conception
de la **8.1.1**, à revérifier à son lancement :

- **Scan** : un CD dans un zip ou un `.7z` n'est plus refusé (`ZIPPED_DISC` disparaît) : il devient un jeu du
  système deviné, marqué « archivé » par son extension de chemin (pas de colonne). Pas de sonde, pas de CRC de
  piste au-delà de l'en-tête (le scan ne remplit pas de cache). `needs_32x` = `name_needs_32x` (formes normalisées
  de la 7.5, `(32X)` nu refusé, D9) ou marque manuelle `[library] cd32x`.
- **Lancement** : `LaunchRefusal::ArchivedDisc` est remplacé par une demande `ArchivedDiscOffer { bytes }` (taille
  déclarée) que l'UI montre (« Extraire ce CD (≈ N Mo dans le cache, première fois lente) » ou annuler avec
  l'explication) ; place manquante : éviction des copies évinçables (§3.1, T1-3) ; borne
  `MAX_ARCHIVE_FILE_BYTES` revue pour les gros CD ; plus gros que le plafond entier : refus « augmentez le cache
  dans les Réglages » ; l'extraction reste dans le cache, jamais dans `roms/` (Z2).
  Après accord : extraction complète dans la copie de travail, `.cue` réécrit pour pointer les pistes extraites,
  puis **sonde `32X Initial Program`** (`disc_needs_32x`) sur la piste de données extraite, **avant**
  `choose_game_core`. `GameNeeds::needs_32x` = colonne ou marque manuelle ou sonde ; le résultat de la sonde est
  écrit dans `game.needs_32x` (`Library::set_needs_32x(game_id, bool)`, `emu-library`). Picodrive absent :
  message 7.5 inchangé (« picodrive requis, jamais de repli sur genesis_plus_gx »).
- La sonde de disque (`SEGADISCSYSTEM`, `disc_info`) et l'identification Redump par piste 01 sont aussi passées
  sur la copie extraite ; elles ne changent jamais le système d'un jeu déjà rangé (règle `known_game`).
- Tests 8.1.1 : CD de test archivé (`mkcd.py --variant 32x` mis en zip et en `.7z`).

### 9.4 Contrat 7.5 (Journal, messages copiables, fichiers d'origine, config)

- **`firmware_advice`** (contrat 7.5 §8) : inchangée ; elle dépend du core, du système et de la variante, pas du
  conteneur. Si la variante dépend des extensions du contenu (`launch_firmware`), elle lit le `.7z` par
  `list_extensions`.
- **Erreurs d'extraction** : un type `ArchiveError` (`emu-runtime`, `#[non_exhaustive]`) — `Encrypted`,
  `TooLarge` (taille déclarée, total ou fichier d'archive au-delà des bornes), `DictionaryTooLarge` (mémoire des
  codeurs), `CrcMismatch`, `DiskFull` (sans champs : place non mesurée), `Corrupt` (dont octets décodés au-delà de
  la taille déclarée), `Cancelled` — converti par `emu-ui` en `UserMessage { what, fix }` (7.3) rendu par
  `theme::error_box` avec `copyable::copy_button` (texte = message + chemin de l'archive). Chaque erreur est aussi
  écrite au Journal (`tracing::error!`, cible `emu_runtime::archive`), donc comptée dans le bouton du pied de page.
  `Cancelled` : `info`, aucun message d'erreur.
- **Réglages** : clé `[library] archive_cache_mb` (défaut **2000**, minimum **1000**) ; absente = défaut ; valeur
  sous le minimum ramenée au minimum ; test d'aller-retour avec un `config.toml` de la 7.5, de la 7.6 et de la 8.0
  (la 8.0 ne l'écrit pas, design 8.0 §0.1).
- **Manuel** (`docs/manuel.md`, embarqué) : paragraphe « Archives `.7z` » (T4) ; limites 8.1 : CD archivés,

## Décisions de l'utilisateur (2026-11-24, priment sur ce qui précède ; périmètre précisé le 2026-11-27)
