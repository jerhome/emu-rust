# Version 5.0 — Amstrad CPC et Commodore 64 : contrat et découpage

Décisions : **ADR 0019** (statut **accepté** le 2026-11-21, après re-validation contre le code : §10 ; précise 0005, 0013, 0014).
Étude d'essais : `docs/essais-cpc-c64.md`. Base réutilisée : `docs/design/v2.0-atari-st.md` (infrastructure
« ordinateur »), `v3.0-amiga.md` (`MediaRules` / `media_direct`, import de BIOS, `[remap]`, `DatSource::Libretro`,
et les **règles communes du §3.5** : ordre d'évaluation des médias, `folder_extensions`, `game_saves` /
`reset_core_game_files`, défauts calculés, contrôle de firmware avec `FirmwareState::Builtin`, notices),
`v4.0-dos.md` (`featured_options` par système, `layout_option`, `.m3u` étendu). Ce document ne donne que le **delta**
par rapport à la 4.0. Les signatures seront **posées dans le code par l'`architecte` au lancement de la 5.0** (tâche
CX0), quand les crates bas de la 4.0 sont fusionnés (plan d'harmonie, `docs/design/integration-largeur.md`) ;
**posées le 2026-11-21 sur `wip-5.0`** (le code fait foi ; écarts : §11). **Re-validation du 2026-11-21 contre le code réel (3.0, 2.1) : §10 —
en cas de divergence avec un passage antérieur, le §10 prime.**

Révision du 2026-11-21 : ROM C64 intégrées **acceptées** par l'utilisateur ; mode d'entrée par défaut **Joystick**
pour ces deux systèmes (`default_input`) ; clé `save_dir = "game"` renommée **`save_scope`** ; `#COMMAND:` d'un `.m3u`
utilisateur jamais recopié pour VICE ; `builtin_firmware`, `layout_option`, `folder_extensions` ne sont plus posés
ici (3.0 / 4.0) : la 5.0 n'en fournit que les données.

Livraison (décision utilisateur du 2026-11-20) : **jalon CPC** ⇒ pré-release `v5.0.0-rc.1` et essai ; **jalon C64**
⇒ `v5.0.0-rc.2` (pas de tag stable séparé : la stable est la dernière rc validée par l'essai de l'utilisateur,
décision du 2026-11-21). Si le C64 bloque (core instable), la 5.0 reste au CPC seul et le C64 passe en 5.1. Toute l'infrastructure générique est livrée par le jalon CPC : le jalon C64 n'ajoute que des
données, un système de bibliothèque et l'interface propre au C64.

## 2. Fonctionnement

### 2.1 Lancement d'un jeu CPC

```text
Game (cpc) ─ choose_core ─► cap32 (save_scope = "game", fastforward_override = true)
options : défauts core < cores.toml < calculés [cap32_lang_layout = f(langue) ; .cpr ⇒ cap32_model = "6128+"]
          < [core_options.cap32] < game-options/cap32/<jeu>.toml
contenu : MediaSet (dsk / cdt / voc / sna / cpr, zip extrait, groupe Side A/B, .m3u)
          rules = MediaRules { policy: Direct, m3u_launch: Command, … } (ordre d'évaluation : 3.0 §3.5.1) ; launch = options.media.launch
          ─► sans launch, une image ⇒ ContentSpec::File(image) ; sinon .m3u généré (dossier privé) :
             #COMMAND:RUN"DISC
             /chemin/absolu/Jeu (Side A).dsk|Face A
             /chemin/absolu/Jeu (Side B).dsk|Face B
EmulatorOptions.core_save_scope = Game ⇒ GET_SAVE_DIRECTORY = identity.core_save_dir = saves/cap32/<save_name>/   (identité 2.1)
core : autorun (catalogue + base clean-cpc-db) ; écritures disquette ⇒ saves/cap32/<jeu>/<image>.sav (différentiel)
cassette : le core tape RUN" ; pendant la lecture il demande l'avance rapide (env 64) ⇒ OSD « Chargement accéléré »
mode d'entrée initial = mémorisé par jeu, sinon [computer] keyboard_mode s'il vaut keyboard / joystick, sinon (auto) default_input du système = Joystick
```

### 2.2 Lancement d'un jeu C64

```text
Game (c64) ─ choose_core ─► vice_x64 (ou vice_x64sc) (fastforward_override = true, variable_state_size = true)
options : défauts core < cores.toml (mappers neutralisés, datasette sur F13-F15, autoloadwarp) < config < jeu
contenu : MediaSet, rules = MediaRules { policy: WorkingCopy, media_direct: [], m3u_launch: Program }
          ─► copies dans saves/<core>/<jeu>.disks/ (noms d'origine conservés : tags (j1), NTSC, (MD) lus par le core)
          (zip extrait par le frontend malgré block_extract = 1 : sinon VICE extrait dans saves/TEMP, écritures perdues)
          ─► launch = "INTRO" ⇒ .m3u : « Jeu.d64:INTRO »
modèle NTSC (option du jeu ou tag) ⇒ SET_SYSTEM_AV_INFO à chaud (384×247, 59,83 i/s) ⇒ av_info_changed (chemin 1.0)
core : autostart (LOAD"*",8,1 / LOAD cassette + RUN / PRG injecté) ; warp pendant les accès ⇒ env 64
RetroPad port 0 ⇒ port C64 = vice_joyport (jeu, défaut 2) ; mode d'entrée initial = Joystick (default_input), sauf jeu mémorisé
```

### 2.3 Cassette

```text
menu (touche hôte) ▸ Cassette ▸ Lecture | Arrêt | Rembobiner
   ─► CorePreferences::actions(core).tape_play = "HOME" (cap32) | "F13" (vice)
   ─► RetroKey::from_name ─► Emulator::pulse_key(key, PULSE_FRAMES = 4)
        image n   : KeyboardState[key] = true + KeyEvent { down: true }
        image n+3 : KeyboardState[key] = false + KeyEvent { down: false }
   ─► OSD « Cassette : lecture »
```

### 2.4 Chargement accéléré (env 64)

```text
core (pendant retro_run) ─ SET_FASTFORWARDING_OVERRIDE { fastforward: true, ratio, notification, inhibit_toggle }
   ─► emu-libretro (si CoreConfig::fastforward_override) : mémorise, renvoie true ; RunEvents::fastforward = Some(…)
   ─► FrameStatus::fastforward_changed ─► UI : Speed::FastForward { ratio > 0 ? ratio : ratio 2.0 } ; son coupé ;
      OSD « Chargement accéléré » ; touche d'avance rapide ignorée si inhibit_toggle
core ─ { fastforward: false } ─► retour à Speed::Normal (sauf si l'utilisateur tenait l'avance rapide)
GET_FASTFORWARDING répond l'état effectif (le core le lit : cap32 rend la main si l'utilisateur l'a coupée)
[computer] auto_fast_load = false ⇒ CoreConfig::fastforward_override = false pour tous les cores
```

### 2.5 Port joystick C64

```text
menu ▸ « Port joystick : 2 » ─► bascule 1 ⇄ 2 ─► Emulator::set_option("vice_joyport", "1") (appliquée par le core
   à GET_VARIABLE_UPDATE) + game-options [core_options] vice_joyport = "1" ─► OSD « Joystick sur le port 1 »
nom de fichier avec (j1) / (j2) ─► le core ignore l'option jusqu'au redémarrage : le menu affiche « fixé par le nom »
```

## 3. Interfaces entre crates (delta 4.0 → 5.0)

### 3.1 `emu-libretro`

```rust
pub struct CoreConfig { …, pub fastforward_override: bool,      // défaut false : 64 → false (comportement 4.0)
                         pub variable_state_size: bool }       // défaut false ; true ⇒ comme SerializationQuirks::CORE_VARIABLE_SIZE
#[non_exhaustive] pub struct FastForwardOverride { pub ratio: f32, pub fastforward: bool, pub notification: bool, pub inhibit_toggle: bool }
RunEvents += pub fastforward: Option<FastForwardOverride>      // dernière demande vue pendant ce run
impl Core { pub fn fastforward_override(&self) -> Option<FastForwardOverride>; }  // état courant (demande hors run comprise)
```

Règles : 64 avec `data == NULL` ⇒ `true` si `fastforward_override` (le core teste la prise en charge, VICE le fait dans
`retro_init`), `false` sinon ; avec données : copie de la structure (`ratio` non fini ou négatif ⇒ 0.0 = « rythme du
frontend »), `true`. Une demande hors `retro_run` (chargement) est mémorisée et rapportée au run suivant.
`GET_FASTFORWARDING` (49, déjà servi) répond l'état effectif que l'UI fixe par `Core::set_fast_forwarding` (existant).
`variable_state_size` : `unserialize` accepte un état plus court que `serialize_size()` courant (VICE : la taille
dépend du support inséré, sans `SET_SERIALIZATION_QUIRKS`) ; `serialize` relit déjà la taille à chaque appel.
Le bloc `unsafe` qui lit `retro_fastforwarding_override` suit la règle 2.0 (pointeur non nul, alignement, durée de
l'appel). La constante `sys::RETRO_ENVIRONMENT_SET_FASTFORWARDING_OVERRIDE` existe (= 64, **sans** drapeau expérimental, posée
par F3 qui répond `false`) : CF1 remplace cette réponse par l'opt-in.

### 3.2 `emu-runtime`

```rust
pub enum SaveScope { Core, Game }                                   // défaut Core (4.0)
pub struct EmulatorOptions { …, pub core_save_scope: SaveScope, pub fastforward_override: bool, pub variable_state_size: bool }
pub enum M3uLaunch { None, Command, Program }                       // défaut None
pub struct MediaRules { …, pub m3u_launch: M3uLaunch }
pub struct MediaSet { …, pub launch: Option<String> }
pub const PULSE_FRAMES: u32 = 4;
impl Emulator {
    pub fn pulse_key(&mut self, key: RetroKey, frames: u32);         // frames < 2 ⇒ 2
    pub fn fastforward_override(&self) -> Option<FastForwardOverride>;
    // dossier réellement donné au core : `self.identity().core_save_dir` (2.1) ; pas de `core_save_dir()` en double
}
FrameStatus += pub fastforward_changed: bool
RuntimeError += InvalidLaunch(String)
```

Règles :
- `SaveScope::Game` : **même mécanisme que l'identité de jeu de la 2.1** (`docs/design/v2.1-identite-disques.md` §2.1 et
  §6), dont il ne fait que forcer la branche « sous-dossier » : `IdentityRequest` gagne `scope: SaveScope` et
  `resolve_game_identity` rend `core_save_dir = <saves>/<core_id>/<save_name>/` pour **tous** les jeux du core (index 1
  compris), au lieu des seuls homonymes. `<save_name>` = nom nu, ou `<jeu> (n)` pour un homonyme. Dossier créé avant
  `Core::load`. SRAM, savestates, `.disks` et registre restent à plat sous `<saves>/<core_id>/`. Aucun autre calcul de
  chemin dans `emulator.rs`.
- `pulse_key` : met en file un appui ; pendant `frames` images le `KeyboardState` de la touche est vrai, un
  `KeyEvent` d'appui est livré au début et un de relâchement à la fin (même chemin que `InputFrame::key_events`,
  hors `retro_run`, ADR 0015) — **les deux** sont nécessaires : cap32 et VICE ne lisent les touches que par le
  callback 12 (mesuré), mais les raccourcis `vice_mapper_*` (cassette F13-F15) sont lus par interrogation ;
  plusieurs impulsions en file se suivent sans chevauchement ; une touche réellement
  tenue par l'utilisateur n'est pas relâchée par l'impulsion. Ne passe jamais par la touche hôte ni le remappage.
- `launch` : `None` ou vide ⇒ comportement 4.0. Sinon : ASCII imprimable, ≤ 64 caractères, sans `\r` / `\n`
  (`InvalidLaunch` sinon) ; `Program` : en plus sans `:` `|` `#`. Un `.m3u` de travail est **toujours** généré
  (dossier privé en `Direct`, `<jeu>.disks/` en `WorkingCopy`) : `Command` ⇒ première ligne `#COMMAND:<launch>` ;
  `Program` ⇒ première entrée `<image>:<launch>`. `M3uLaunch::None` avec `launch` ⇒ `InvalidLaunch`.
- `.m3u` utilisateur relu (2.0) : lignes `#` filtrées par la **liste blanche** du design 3.0 §3.5.1 (`#SAVEDISK:`,
  `#LABEL:` conservés à leur place ; suffixe `|libellé` conservé ; toute autre ligne `#` écartée). `#COMMAND:` :
  `M3uLaunch::Command` ⇒ conservé s'il passe la validation de `launch` (sinon écarté + `warn!`), remplacé si `launch`
  est défini ; **`M3uLaunch::Program` ou `None` ⇒ jamais recopié** (VICE : arguments de ligne de commande du core).
  `PreparedMedia` gagne `dropped_lines: u32` (R3 ne fait que les journaliser), affiché une fois par l'OSD. La liste
  blanche existe (R3, `KEPT_DIRECTIVES` de `media.rs`) et écarte toujours `#COMMAND:` : CR1 la rend conditionnelle.
  **Règle `Direct` (revue V3a)** : `media.rs` transmet aujourd'hui un `.m3u` utilisateur tel quel en `Direct`, sans liste
  blanche ; un `#COMMAND:` atteindrait alors VICE. Décision : dès qu'un core déclare `m3u_launch` (quelle que soit
  sa politique), tout `.m3u` utilisateur est **relu et régénéré** avec la liste blanche (dossier privé en `Direct`) ;
  jamais transmis tel quel. De plus VICE reste en `working_copy` (défense en profondeur).
- `Direct` avec images référencées en absolu et zips inspectés puis extraits quand ils contiennent une image
  acceptée : ordre d'évaluation du design 3.0 §3.5.1, inchangé (cap32 n'extrait pas ; VICE extrairait dans
  `saves/TEMP` et perdrait les écritures). `.m3u` généré en `Direct` : dossier temporaire privé (3.0 §3.5.1).
- `FrameStatus::fastforward_changed` : vrai quand `Core::fastforward_override` change pendant l'image.

### 3.3 `emu-assets`


Règles : noms d'actions validés au chargement de `cores.toml` contre une liste de noms `RETROK` (copie de chaînes :
`emu-assets` ne dépend pas d'`emu-libretro` ; la conversion se fait dans l'UI par `RetroKey::from_name`) ;
`options_by_extension` : extension en minuscules sans point (troisième source de la couche « défauts calculés »,
3.0 §3.5.4). **`game_saves`** : un motif sans `{game}` (`*.sav`) n'est accepté au chargement de `cores.toml` que pour
un core `save_scope = "game"` (le validateur de la 3.0, `is_save_pattern`, l'accepte partout : sur un dossier commun
il effacerait les fichiers des autres jeux). Un core avec `builtin_firmware` et des firmwares facultatifs dans son `.info` (VICE :
JiffyDOS) affiche `Builtin` pour le système et l'état habituel (`Missing` facultatif, `Ok`…) pour chaque fichier.

Règles : `folder_extensions` et l'attribution des extensions partagées sont ceux du design 3.0 §3.5.2, sans code

`(Tape N of M)` / `(Tape N)`. Zips : système déduit des entrées (1.0) ; un zip contenant à la fois `.dsk` et `.d64`
est ignoré (compté). **Migration de schéma : aucune** (schéma v5 de la 4.0 ; les deux DAT du CPC utilisent la clé
`(system, source)` de la v4).

## 4. `emu-ui` / `emu-app` (agent `ui`)

```rust
// computer/eightbit.rs — pur, testé
// `layout_value` (4.0) et `computed_options` (3.0, computer/computed.rs) existent : la 5.0 ajoute la source
// `options_by_extension` à `computed_options` et les données `layout_option` de cap32 ("fr-FR" ⇒ "french").

ComputerConfig += pub keyboard_mode: KeyboardModeSetting                          // nouvelle clé `[computer] keyboard_mode`
// L'ancienne clé `default_keyboard_mode` (2.0-4.0) n'est plus écrite. Relue pour migration seulement :
```

| Risque | Atténuation |
|---|---|
| ROM C64 sans permission connue (Debian les retire) | **Acceptées par l'utilisateur (2026-11-21)** ; notice dans l'écran Cores et le README ; rien n'est extrait ni redistribué (règle « Builtin », ADR 0005) |
| Raccourcis codés en dur de cap32 (`F9`, `F10`, Début, Fin, Pg↑, Inser) | Surcharge F1-F12 ⇒ pavé (F9 / F10 n'atteignent plus le core) ; Début / Fin / Pg↑ = touches cassette (voulu) ; Inser documentée ; nightly surveillée par les tests réels |
| Différentiel cap32 nommé par le nom de base de l'image | Dossier de sauvegarde par jeu (`save_scope = "game"`, chemin de l'identité 2.1) ; tests de non-collision : deux jeux avec `DISK1.DSK`, et deux jeux **homonymes** (`Jeu (2)/`) |
| VICE : `RCTRL` (port), `END` (reset) et `Select` (clavier virtuel) par défaut | Options neutralisées dans `cores.toml` ; test réel : £ par Fin, Ctrl droit sans effet sur le core |
| `vice_joyport` ignorée après un tag `(j1)` ou la bascule du core | Menu « fixé par le nom » ; raccourci du core neutralisé |
| `vice_x64sc` ≈ 5× plus lent que `vice_x64` (7,1 s contre 1,4 s pour 2 000 images ici) : risque sur l'Iris Xe et le Mac Intel, gain du chargement accéléré borné | `vice_x64` par défaut ; x64sc installable ; temps par image journalisé en KQ2 et pendant l'essai (OSD de débogage) |
| Géométrie / cadence changées à chaud (NTSC) ; taille d'état variable (VICE) | Chemin `av_info_changed` (1.0) testé ; `variable_state_size` ; tests réels KQ2 |
| Dossier système en lecture seule (VICE réécrit `system/vice/vicerc-dump-C64`) | Volume `/data` en écriture ; journal d'erreur seulement, documenté |
| Cadences 50,08 Hz (CPC) / 50,12 Hz (C64 PAL) sur écran 60 Hz | Synchro audio ADR 0010 (déjà en place pour ST / Amiga) |
| Chargements cassette de plusieurs minutes si l'env 64 échoue | `cap32_tape_fastload` (interne au core) ; VICE `vice_autostart = warp` par jeu ; avance rapide manuelle 2.0 |
| Avance rapide demandée par le core et tenue par l'utilisateur en même temps | Règle §2.4 : l'utilisateur garde la main si `inhibit_toggle` est faux ; `GET_FASTFORWARDING` toujours exact |
| Images C64 des collections non identifiées (No-Intro = surtout `tap` / `nib` / `crt`) | Repli sur le nom (1.0), jaquettes par titre ; ScreenScraper par nom de fichier |
| Lignes `#COMMAND:` / `launch` hostiles (injection de lignes dans le `.m3u` ; arguments VICE arbitraires dans un `.m3u` de collection) | Validation stricte (ASCII imprimable, sans fin de ligne, longueur) ; liste blanche des lignes `#` ; `#COMMAND:` jamais recopié pour VICE ; revues CV1 et KV1 |
| Mode Joystick par défaut : ZQSD / J / K ne tapent plus de texte (jeu qui demande une saisie) | OSD au lancement, Ctrl droit + J mémorisé par jeu, entrées BASIC en Clavier |
| Alt + F4 / Alt + Tab / Alt + Espace interceptés par Windows (COPY, RESTORE sur Alt / AltGr) | Guide d'essai ; clavier virtuel |

## 9. Questions pour l'utilisateur (défaut appliqué sans attendre ; recommandation entre parenthèses)

Tranchées le 2026-11-21 : q.1 (ROM C64 acceptées) et q.3 (Joystick par défaut). Les autres gardent le défaut
recommandé, à confirmer au lancement de la 5.0.


1. **[DÉCIDÉ — utilisateur, 2026-11-21 : acceptées, « il faut que ça marche de suite »]** **ROM C64 intégrées au core VICE** : Amstrad autorise explicitement la redistribution des ROM CPC, Commodore
   jamais ; VICE les fournit depuis 30 ans, Debian les retire. emu-rust télécharge le core officiel tel quel (comme
   RetroArch) sans jamais extraire ni copier les ROM. Acceptes-tu ce cas pour le C64 ? (*oui*, avec la notice
   affichée ; **sans réponse, le jalon C64 ne démarre pas**, le CPC si.)
2. **Core C64** : `vice_x64` (rapide) par défaut, `vice_x64sc` (exact au cycle, ≈ 5× plus lent : 7,1 s contre 1,4 s
   pour 2 000 images ici) en alternative installable ? Sur ton portable Iris Xe et ton Mac Intel, x64sc risque de
   manquer de marge, surtout pendant les chargements accélérés. (*x64* ; x64sc pour les démos ou si tu constates un
   défaut d'affichage précis.)
3. **[DÉCIDÉ — utilisateur, 2026-11-21 : Joystick pour CPC et C64, champ `default_input` ; le défaut provisoire « Clavier » ci-dessous est caduc]** **Mode d'entrée par défaut** des jeux CPC / C64 : la 2.0 a fixé *Clavier* (jeux ST à la souris), mais les jeux
   8 bits sont surtout au joystick et l'autorun évite de taper `RUN"`. *Joystick* (ZQSD + J / K) par défaut pour ces
   deux systèmes, *Clavier* pour les entrées BASIC ? (*Joystick* ; défaut appliqué en attendant : *Clavier*, mémorisé
   par jeu après un Ctrl droit + J.)
4. **Chargement accéléré automatique** des cassettes et disquettes (le son est coupé pendant le chargement) ?
   (*oui*, désactivable dans les Réglages.)
5. **Touches** : sur le CPC, F1-F10 du Razer (Fn + chiffres) = touches f1-f0 du pavé CPC, Alt = COPY ; sur le C64,
   AltGr = RESTORE, `<` = £, Échap = RUN/STOP, Ctrl gauche = C= . Ton Razer a-t-il une touche `²` (sinon ← du C64 via
   le clavier virtuel) ? (*ces correspondances* ; réponse sur `²` à l'essai.)
6. **CPC en français** quand le système est en français (ROM et clavier AZERTY du CPC 6128 français), réglable par
   jeu ? (*oui*.)
7. **Cartouches CPC+ / GX4000** (`.cpr`, modèle 6128+ choisi automatiquement) dans la 5.0, sans garantie ?
   (*oui*.)
8. **JiffyDOS** (commercial, chargements disque rapides) : le possèdes-tu ? Il s'importerait par « Importer un
   BIOS… ». (*question d'information* ; l'avance rapide automatique couvre l'essentiel.)
