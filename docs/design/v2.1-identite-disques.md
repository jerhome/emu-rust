# Version 2.1 — Identité de jeu, disquettes ajoutées mémorisées : contrat et découpage

Statut : **proposé** (2026-11-21). Complète la 2.1 (manette : `docs/design/phase6-manette.md`, T2 à T7). Précise
ADR 0011 (« nom de jeu », SRAM, états) et ADR 0015 §5 (copies de travail) : ces deux ADR seront **amendées par la
tâche I0** (section « Amendement 2.1 », pas de nouvelle ADR tant que l'harmonie n'a pas attribué de numéro ; 0021
est réservé à la 7.0). Origine : `docs/questions-ouvertes.md`, lignes « 2.0 — disquettes ajoutées » (2026-11-20) et
« 2.1 — sauvegardes et états indexés par nom de jeu seul » (2026-11-21).

Aucune signature n'est posée dans le code aujourd'hui (un agent `ui` travaille sur `emu-ui` / `emu-app`, R3 de la
3.0 sur `emu-runtime/src/media.rs`) : elles le seront par I0. **Aucune migration de `library.sqlite`** (la 2.1
reste au schéma v3) : l'identité vit dans les dossiers de sauvegarde, pas dans la bibliothèque. Graphe des crates
inchangé ; aucun `unsafe` ; aucun code réseau.

## 1. Constat (code livré, rc.2)

| Donnée | Clé aujourd'hui | Fichier |
|---|---|---|
| SRAM | `<saves>/<core_id>/<jeu>.srm`, `<jeu>` = nom du fichier (ou du jeu de disques) | `emu-runtime/src/saves.rs` (`sram_path`) |
| États | `<states>/<core_id>/<jeu>.state0…9` ; en-tête `core_id`, `core_version`, `game`, `created_unix` | `saves.rs` (`state_path`, `StateHeader`) |
| Options par jeu | `<data>/game-options/<core_id>/<jeu>.toml` | `emu-ui/src/game_options.rs`, `content.rs` (`game_key`) |
| Copies de travail | `<saves>/<core_id>/<jeu>.disks/`, puis `<jeu> (n).disks/` ; manifeste `.emu-rust-disks` (source = chemin + taille + date + CRC32) | `emu-runtime/src/{media,workcopy}.rs` |
| Dossier donné au core (`GET_SAVE_DIRECTORY`) | `<saves>/<core_id>/` | `emulator.rs` |

- Deux jeux homonymes (`Jeu1/disk1.st`, `Jeu2/disk1.st` ; deux `Game.sfc` de dossiers différents) ont des copies de
  travail **séparées** (rc.2) mais **partagent** `.srm`, états et options : charger l'état de l'un dans l'autre
  réécrit les copies de l'autre.
- Disquettes ajoutées par le menu : depuis la rc.2 le manifeste retient la source de chaque copie ajoutée
  (`Origin::Added`) et **réutilise la copie** quand la même source est ajoutée de nouveau. Il reste que : (1) la
  disquette n'est pas reproposée à la session suivante (il faut ressaisir son chemin, et `media.last_disk` peut
  désigner un index qui n'existe plus) ; (2) les copies de la rc.1 (`02 X.st`, `03 X.st`…) et celles « oubliées »
  au-delà de 32 restent sur le disque sans que rien ne les montre ; (3) rien ne permet d'en retirer une.
- Core inconnu (`--core /x/y.so`) : un `.zip` n'est l'extension d'aucun système, donc `content_spec` le traite
  comme « pas sûrement une cartouche » et demande une copie de travail, même pour une ROM de console.

## 2. Décisions

### 2.1 Identité de jeu : un nom de sauvegarde (`save_name`) attribué une fois, tenu dans un registre

**Clé retenue : le nom actuel, départagé par un suffixe ` (n)`, attribué par un registre par core.** Le premier jeu
qui porte un nom garde le nom nu (`<jeu>`) ; un homonyme reçoit `<jeu> (2)`, `<jeu> (3)`… Ce `save_name` remplace
`<jeu>` **partout** : `.srm`, états, options par jeu, dossier `.disks`, dossier de sauvegarde propre au jeu.

Pourquoi pas un hash de chemin ou l'identifiant de bibliothèque dans le nom de fichier :

| Option | Rejetée parce que |
|---|---|
| `<jeu> [hash du chemin]` pour tous | renomme tous les fichiers 1.0 / 2.0 (migration risquée), casse l'interopérabilité RetroArch des `.srm`, perd les sauvegardes dès qu'un dossier de ROMs est déplacé |
| `GameId` de la bibliothèque | `emu-runtime` ne dépend pas d'`emu-library` ; l'identifiant ne survit pas à une base mise en quarantaine ; les lancements en ligne de commande n'en ont pas |
| hash du contenu seul | deux copies identiques dans deux dossiers seraient confondues ; coûteux pour un CD ; une ROM remplacée (patch, traduction) perdrait ses sauvegardes, contrairement à la 1.0 |

Le registre donne : **zéro renommage** pour les jeux non homonymes (≈ tous), des noms lisibles, la compatibilité
RetroArch et 1.0 / 2.0 conservée, et le même schéma que les dossiers `<jeu> (n).disks` déjà livrés.

**Registre** : `<saves>/<core_id>/.emu-rust-games` (texte borné, même style que `.emu-rust-disks` : en-tête
`emu-rust games 1`, une ligne par `save_name`). Champs : `base` (nom 1.0 / 2.0), `index` (1 = nom nu), clé de
chemin canonique de la **source principale**, taille, date, empreinte, drapeau `legacy` (§2.2). Lecture-modification-
écriture sous verrou inter-processus (`<saves>/<core_id>/.emu-rust-games.lock`, `File::lock`, repli journalisé comme
pour les cores) ; écriture atomique. Registre illisible ou trop gros (> 8 Mio) : jamais réécrit, copie
`.corrupt-<unix>`, et la session retombe sur le **comportement 2.0** (nom nu) avec un avertissement.

**Source principale** : `ContentSpec::File` ⇒ le fichier (l'archive pour un zip) ; `Media` ⇒ le `.m3u` de
l'utilisateur s'il y en a un, sinon la première image ; un CD ⇒ son `.cue` / `.chd` / `.iso` (jamais les pistes) ;
`NoGame` ⇒ aucune : identité fixe `no-game`, hors registre.

**Empreinte** : taille + CRC32 du fichier entier s'il fait ≤ 64 Mio, sinon taille + CRC32 du premier et du dernier
Mio (images CD, `.hdf` : jamais de lecture de centaines de Mo). Calculée à la création de l'entrée et seulement quand
une comparaison l'exige (un lancement normal ne fait qu'un `stat`, comme `workcopy.rs`). CRC32 suffit : la menace
est une confusion honnête, pas une falsification.

**Résolution** de (`base`, source `P`), dans cet ordre :

1. une entrée a la **même clé de chemin** ⇒ c'est elle, même si le contenu a changé (une ROM remplacée au même
   endroit garde ses sauvegardes, comme en 1.0) ; taille / date / empreinte rafraîchies ;
2. sinon une entrée a la **même empreinte** et son chemin enregistré **n'existe plus** ⇒ fichier déplacé ou dossier
   renommé : c'est elle (le chemin est mis à jour). Vaut aussi quand le fichier a été **renommé** (autre `base`) :
   les sauvegardes suivent, le `save_name` reste l'ancien. Si l'ancien chemin existe encore, ce sont deux jeux ;
3. sinon **reprise d'un dossier 2.0** : un `base.disks` ou `base (n).disks` dont le manifeste contient une copie
   `Set` de cette source (chemin, ou taille + CRC) et dont le nom n'est pas déjà au registre ⇒ `save_name` = nom du
   dossier (le jeu qui possédait `G (2).disks` devient `G (2)`, sans rien déplacer) ;
4. sinon **attribution** : `base` s'il n'est pas au registre — **y compris quand des fichiers 1.0 / 2.0 de ce nom
   existent** (adoption : c'est la migration du cas courant, sans aucune écriture hors registre) ; sinon le plus petit
   `n ≥ 2` tel que `base (n)` n'est ni au registre ni le radical d'un fichier ou dossier existant dans
   `<saves>/<core_id>/`, `<states>/<core_id>/` (pas de capture d'un fichier étranger).

Clé de chemin : celle de `workcopy.rs` (octets du chemin canonique sous Unix) ; sous Windows, casse repliée et
préfixe `\\?\` retiré (règle la ligne « casse Windows » de `questions-ouvertes.md` pour ce registre ; le format du
manifeste `.emu-rust-disks` existant n'est pas modifié).

**Dossier de sauvegarde du core** (`GET_SAVE_DIRECTORY`) : `<saves>/<core_id>/` pour un index 1 (inchangé) ;
`<saves>/<core_id>/<save_name>/` pour un homonyme (index ≥ 2). Raison : les fichiers qu'un core écrit lui-même
portent le **nom du contenu** qu'on lui passe (`disk1.save1.adf`, `Game.brm`, `Game.pure.zip`), que le frontend ne
peut pas renommer pour un fichier transmis en place ; deux homonymes se les partageraient. `.srm`, états et
`.disks` restent à plat, sous leur `save_name`. C'est la même formule que le `save_scope = "game"` de la 5.0
(`saves/cap32/<jeu>/`), qui devient « toujours » au lieu de « homonymes seulement » (§6).

**États** : l'en-tête gagne la ligne `game_fp=<taille>:<crc32>` (empreinte de la source principale au moment de la
sauvegarde). Le format reste en version 1 : le lecteur 2.0 ignore les clés inconnues (un état 2.1 se charge en 2.0).
Au chargement : `game_fp` égal ⇒ rien ; différent ⇒ `StateOrigin::OtherContent` ; absent (état 1.0 / 2.0) et `base`
porté par plusieurs entrées du registre ⇒ `StateOrigin::Ambiguous`. Dans ces deux cas l'UI demande confirmation
(« Cet état peut venir d'un autre fichier du même nom : le charger peut modifier les disquettes de ce jeu. »,
défaut **Non**) ; jamais de refus définitif, jamais de suppression.

### 2.2 Migration 1.0 / 2.0 → 2.1 : sans perte, sans renommage

- **Aucun fichier existant n'est renommé, déplacé ni supprimé.** Jeu non homonyme : le registre enregistre le nom
  nu au premier lancement, les fichiers existants sont les siens. Retour à la 2.0 : tout est relu tel quel.
- Homonymes déjà joués en 2.0 (ils partageaient `G.srm`, `G.state*`, `G.toml`) : impossible de savoir à qui est
  quoi. Le jeu qui possède `G.disks` (règle 3) ou, à défaut, le premier lancé en 2.1 garde `G` et ses fichiers ;
  l'entrée est marquée `legacy` si des fichiers de ce nom existaient avant elle. Le suivant reçoit `G (2)` et :
  - **`.srm` et options par jeu : copiés** (`G.srm` → `G (2).srm`, `G.toml` → `G (2).toml`, seulement si la cible
    est absente et l'entrée 1 `legacy`) : chacun retrouve exactement ce qu'il voyait en 2.0 ;
  - **états : non copiés** (c'est le cas dangereux) ; ils restent à `G`, et un bandeau le dit une fois :
    « Deux jeux s'appellent G : leurs sauvegardes sont maintenant séparées. Les états antérieurs restent attachés à
    <chemin du premier> (`states/<core>/G.state*`). » (question 1, §9) ;
  - dossier de sauvegarde du core : nouveau sous-dossier vide pour `G (2)` ; hatari n'y écrit rien de propre au jeu,
    donc rien à reprendre en 2.1.
- Dossier `.disks` sans manifeste (rc antérieures) : règle 2.0 inchangée (adopté par le premier jeu préparé).
- Un `<jeu> (n).disks` créé pour `SourceChanged` (image remplacée) reste géré par `choose_work_dir` : l'identité ne
  change pas (règle 1), seules les copies changent de dossier, comme aujourd'hui.

Compatibilité : 2.0 ← 2.1 sans perte pour les noms nus ; les fichiers `G (2).*` sont ignorés par une 2.0 (qui
retrouve le partage d'avant). RetroArch : `.srm` au nom nu inchangés.

### 2.3 Disquettes ajoutées : restaurées à chaque session, retirables, nettoyage explicite

- **Restauration** : après le chargement, les copies `Origin::Added` du manifeste dont le fichier existe sont
  rajoutées au core **dans l'ordre d'ajout** (même chemin de code que `Disks::add` : `add_image` +
  `replace_image`, sans insertion), que la source d'origine existe encore ou non (la progression est dans la copie).
  Le menu Disquettes montre donc la même liste qu'à la session précédente et `media.last_disk` reste valide. Les
  noms de fichier ne changent pas : le nom de contenu vu par le core non plus. Sans interface disque : rien.
  Borne : `MAX_MEDIA_IMAGES` au total ; l'« oubli » silencieux au-delà de 32 disparaît (l'ajout est refusé avec un
  message : « retirez une disquette ajoutée »).
- **Retrait** : menu Disquettes, sur une disquette ajoutée non insérée : « Retirer » (sortie de la liste du core et
  du manifeste ; la copie est gardée) ou « Retirer et supprimer la copie » (confirmation, taille et date affichées).
- **Nettoyage** : dialogue « Nettoyer les copies… » du même menu, qui liste les fichiers du dossier `.disks` que
  rien ne référence — copies de la rc.1, copies oubliées, ancienne liste `.m3u` générée — avec taille et date ;
  suppression **uniquement des lignes cochées**, après confirmation. Une copie non référencée peut contenir une
  disquette de sauvegarde : **jamais de suppression automatique**, sauf les temporaires `.tmp-*` de plus d'une heure.
  Chaque copie orpheline a aussi « Reprendre » : elle redevient une disquette ajoutée (entrée `Added` sans source).
- Sessions `File` / `NoGame` : mêmes règles, dans `<save_name>.disks` (`no-game.disks` pour le bureau).
- « Réinitialiser les disquettes » (2.0) inchangé : supprime tout le dossier, disquettes ajoutées comprises (le
  texte de confirmation le dit).

### 2.4 Core inconnu + `.zip` de ROM console : recommandation

**À faire en 2.1** (petit, même fichier que l'identité côté UI). Pour un core absent des préférences, `content_spec`
lit le répertoire central du zip (sans extraction, limites de `content.rs`) : si **toutes** les entrées retenues
(fichiers non vides, hors dossiers) ont une extension de console du catalogue ⇒ `Direct` / `ContentSpec::File`
(comportement 1.0) ; une seule entrée de disquette ou d'extension inconnue, ou un zip illisible ⇒ copie de travail
(choix prudent conservé). Cohérent avec l'ordre des médias de la 3.0 (§3.5.1) : l'UI choisit seulement la politique,
`prepare_media` applique ensuite « zip inspecté ». Sans ce correctif le défaut est bénin (une copie inutile de la
ROM dans `saves/<core>/<jeu>.disks/`), d'où une priorité basse : dernière sous-tâche d'I3.

## 3. Interfaces entre crates

### 3.1 `emu-runtime` (nouveau module `identity.rs` ; ajouts dans `saves.rs`, `workcopy.rs`, `media.rs`)

```rust
// identity.rs
pub struct GameIdentity {
    pub save_name: String,              // <jeu> ou <jeu> (n) : .srm, états, options, <save_name>.disks
    pub index: u32,                     // 1 = nom nu
    pub core_save_dir: PathBuf,         // <saves>/<core_id>/ (index 1) ou <saves>/<core_id>/<save_name>/
    pub notice: Option<IdentityNotice>, // seulement au lancement où l'attribution a lieu
    // + empreinte (privée) pour `game_fp`
}
pub enum IdentityNotice {
    /// Homonyme séparé ; `first` = chemin du jeu qui garde le nom nu ; `sram_copied` : G.srm repris par copie.
    Homonym { first: PathBuf, sram_copied: bool, legacy_states: bool },
    /// Registre illisible : comportement 2.0 pour cette session.
    RegistryUnusable,
}
/// Chemins que l'UI passe ; `primary = None` pour `NoGame`.
pub struct IdentityRequest<'a> { pub saves_core_dir: &'a Path, pub states_core_dir: &'a Path,
                                 pub base_name: &'a str, pub primary: Option<&'a Path> }
pub fn resolve_game_identity(req: &IdentityRequest) -> Result<GameIdentity, RuntimeError>;   // idempotent
pub fn identity_request_for<'a>(spec: &'a ContentSpec, …) -> IdentityRequest<'a>;            // base + source principale
/// Vrai si le nom a été attribué par ce lancement à un homonyme dont l'entrée 1 est `legacy` (l'UI copie alors G.toml).
impl GameIdentity { pub fn inherits_legacy(&self) -> bool; pub fn base_name(&self) -> &str }

// emulator.rs
impl Emulator {
    /// `load_content` (signature inchangée) résout l'identité lui-même ; l'UI, qui en a besoin avant (options par
    /// jeu), la résout puis la passe ici. `set.name` d'un `ContentSpec::Media` est remplacé par `save_name`.
    pub fn load_content_as(core: &Path, spec: ContentSpec, identity: GameIdentity, options: EmulatorOptions)
        -> Result<Self, RuntimeError>;
    pub fn identity(&self) -> &GameIdentity;
    pub fn content_name(&self) -> Option<&str>;        // radical du chemin donné à retro_load_game ({game} de la 3.0)
    pub fn state_origin(&self, slot: u8) -> Option<StateOrigin>;   // None : emplacement vide ou illisible
}
pub struct EmulatorOptions { …, pub restore_added_disks: bool }   // seul champ ajouté ; `true` dans l'UI

// saves.rs
pub struct StateHeader { …, pub game_fp: Option<String> }          // ligne `game_fp=` ; absente = état 1.0 / 2.0
pub enum StateOrigin { Same, OtherContent, Ambiguous, Unknown }    // Unknown : pas de game_fp, pas d'homonyme

// media.rs / workcopy.rs
pub struct AddedDisk { pub copy: PathBuf, pub source: Option<PathBuf>, pub source_present: bool,
                       pub size: u64, pub index: Option<u32> }     // index dans la liste du core, si restaurée
pub enum OrphanKind { Copy, StalePlaylist }
pub struct OrphanCopy { pub name: String, pub kind: OrphanKind, pub size: u64, pub modified: Option<SystemTime> }
impl Disks<'_> {
    pub fn added(&mut self) -> Vec<AddedDisk>;
    pub fn forget_added(&mut self, copy: &Path, delete_copy: bool) -> Result<(), RuntimeError>;   // refusé si insérée
    pub fn adopt_orphan(&mut self, name: &str) -> Result<u32, RuntimeError>;                      // « Reprendre »
}
pub fn orphan_copies(saves_core_dir: &Path, work_dir: &Path) -> Result<Vec<OrphanCopy>, RuntimeError>;
pub fn remove_orphan_copies(saves_core_dir: &Path, work_dir: &Path, names: &[String]) -> Result<u64, RuntimeError>;
// content.rs
pub fn archive_entry_names(zip: &Path) -> Result<Vec<String>, RuntimeError>;   // répertoire central, bornes Limits::DEFAULT
```

Règles : `resolve_game_identity` n'écrit que le registre, son verrou, et les copies d'héritage `.srm` (atomiques,
cible absente seulement) ; `remove_orphan_copies` refuse tout nom qui n'est pas un simple nom de fichier du dossier,
toute entrée référencée par le manifeste, le manifeste lui-même, tout lien, et tout `work_dir` qui n'est pas un
`*.disks` directement sous `saves_core_dir` (garde de `reset_work_dir`). La restauration des disquettes ajoutées
est une étape de `load_content*` (après `retro_load_game`, avant la première image) ; un échec sur une disquette
est journalisé et n'empêche pas le jeu de démarrer.

## 7. Découpage

Règle : un agent par crate, une seule instance par fichier, workspace vert en fin de tâche. Préalable : T3 / T4 de
la manette terminés (`app.rs`, `config.rs` libres).

| Tâche | Agent (modèle) | Fichiers | Dépend de |
|---|---|---|---|
| **I0** Contrat dans le code + amendements ADR 0011 / 0015 | `architecte` (sonnet) | signatures + `todo!()` : `crates/emu-runtime/src/{identity.rs (neuf), saves.rs, media.rs, emulator.rs, content.rs, lib.rs}` ; `docs/adr/0011…`, `0015…` | relecture de ce design par l'harmonie (H1) |
| **I1** Identité, registre, migration, `game_fp` | `runtime-av` (**opus** : écritures, verrou, migration) | `crates/emu-runtime/src/{identity,saves,emulator,workcopy}.rs` | I0 |
| **I2** Disquettes ajoutées (restauration, retrait, orphelins), `archive_entry_names` | `runtime-av` (opus ; **même instance, après I1**) | `crates/emu-runtime/src/{media,workcopy,content,emulator}.rs` | I1 |
| **I3** UI : identité, bandeaux, confirmation d'état, menu Disquettes, zip + core inconnu | `ui` (sonnet) | `crates/emu-ui/src/{content,game_options,app}.rs`, `ui/{disks,menu,text}.rs` | I2, T3 / T4 |
| **I4** Core factice et intégration | `qa-systems` (sonnet) | `tests/mock-core/mock_core.c` (expose le dossier de sauvegarde reçu), fixtures 1.0 / 2.0 / rc.1, `crates/*/tests/` (§5), guide `docs/guide-essai-2.1.md` (section homonymes / disquettes) | fixtures : I0 ; tests : I3 |
| **I5** Revue | `reviewer` (**opus**) | suppressions (`remove_orphan_copies`, `forget_added`), copies d'héritage, registre (verrou, bornes, liens symboliques, noms hostiles), aucune perte sur les arborescences 1.0 / 2.0 | I4 + vérification complète |

Parallélisme : I1 → I2 en série (mêmes fichiers) ; I4 (fixtures, core factice) en parallèle d'I1 / I2 ; I3 seul sur
`app.rs` ; T5 à T7 de la manette (plate-forme, CI) en parallèle de tout. Le Mega CD express s'intègre côté UI
après I3 (même `app.rs`).

Critères de « terminé » : définition de `CLAUDE.md` ; une arborescence 1.0 et une 2.0 rejouées sans qu'aucun
fichier préexistant ne change (hash) ; deux homonymes ont SRAM, états, options et copies distincts ; une disquette
ajoutée réapparaît à la session suivante ; aucune suppression sans action explicite.

## 8. Risques

| Risque | Atténuation |
|---|---|
| Registre perdu ou corrompu : un homonyme reprend le nom nu | Jamais réécrit s'il est illisible ; repli 2.0 signalé ; règle 3 retrouve les `.disks` par leur manifeste ; `game_fp` protège encore les états |
| Mauvaise attribution du nom nu entre deux homonymes déjà joués en 2.0 | Inconnaissable ; `.srm` copié aux deux, états gardés et signalés, rien de supprimé |
| Empreinte partielle identique pour deux gros fichiers différents | Ne sert qu'au cas « ancien chemin disparu » ; taille incluse ; conséquence : un jeu hérite d'un `save_name`, corrigible en déplaçant le fichier |
| Core qui garde des fichiers communs dans son dossier de sauvegarde (config, cartes mémoire partagées) : un homonyme ne les voit plus dans son sous-dossier | Homonymes seulement ; documenté ; aucun core 2.0 concerné |
| Restauration d'une disquette refusée par le core | Journalisée, non bloquante ; la copie reste, visible dans « Disquettes ajoutées » |
| Conflits avec R3 sur `media.rs` / `emulator.rs` | Zones listées au §6 ; I1 / I2 n'y déplacent aucun code existant |
| Windows : verrou de fichier, casse des chemins | Repli journalisé du verrou (comme `cores/.lock`) ; clé de chemin normalisée ; tests CI Windows |

## 9. Questions pour l'utilisateur (défaut appliqué sans attendre)

1. Homonymes déjà joués en 2.0 : copier aussi les **états** au second jeu ? (*Non* : `.srm` et options seulement ;
   les états restent au premier, signalés.)
2. Disquettes ajoutées : les **remettre automatiquement** dans la liste à chaque lancement ? (*Oui*, sans les
   insérer.)
3. Copies non référencées (rc.1) : nettoyage **manuel** par le dialogue, jamais automatique ? (*Oui* : l'une d'elles
   peut être une disquette de sauvegarde.)
4. État d'un autre fichier du même nom : confirmation avec défaut Non, plutôt qu'un refus ? (*Confirmation*.)
