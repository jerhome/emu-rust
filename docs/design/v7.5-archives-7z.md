# 7.5 — Archives `.7z` comme les `.zip` (conception)

Décision utilisateur du 2026-11-24. Projet d'ADR : `docs/adr/0023-archives-7z.md`. Rien n'a pu être vérifié hors
ligne (pas de réseau, pas de build) : les points marqués **[V]** sont à vérifier par `reviewer` / `library-assets`.

## 1. Crate

`sevenz-rust2` (Apache-2.0, pur Rust, fork maintenu de `sevenz-rust`). **[V]** : licence exacte et licences des
dépendances (`cargo deny`/`cargo tree`) ; features : garder LZMA, LZMA2, BCJ/delta, PPMd (`ppmd-rust` : vérifier
qu'il est pur Rust, sinon le retirer), Deflate ; **désactiver** chiffrement AES (`aes256`), et tout codec à
dépendance C (zstd, brotli, bzip2 à écarter sauf preuve de pur Rust) ; version récente, dernière release, issues
ouvertes sur panics en entrée corrompue ; absence d'`unsafe` dans le chemin de lecture (sinon : fuzz minimal).
Repli si rejet : `lzma-rs` + parseur d'en-tête maison (hors budget, pas prévu).
Déclaration : `[workspace.dependencies] sevenz-rust2 = { version, default-features = false, features = [...] }`.
Une archive chiffrée (en-tête ou données) est **refusée** avec un message clair, jamais de mot de passe.

## 2. Scan (`emu-library`)

Le 7z stocke un CRC32 par fichier dans l'en-tête, lisible **sans décompresser** (l'en-tête seul est lu ; il est
lui-même LZMA-compressé mais petit). Stratégie à deux niveaux, ADR 0014/0005 :
- Lister entrées (nom, taille, CRC32, dossier/lien/anti-item) : identification par **CRC32 + taille** contre le
  DAT/libretro-database (qui indexe déjà CRC32 ; sinon retomber sur SHA1).
- SHA1 seulement si l'identification CRC32+taille échoue ou si le DAT n'a que SHA1 : décompression d'une seule
  entrée, bornée (`max` existant, annulation par `cancel`), jamais pour toute l'archive solide si évitable.
- CRC absent (entrée sans CRC) : décompression bornée de cette entrée ; archive solide : une seule passe
  séquentielle, entrées inutiles jetées (le solide impose de décoder le bloc jusqu'à l'entrée).
- Bornes : nombre d'entrées (comme zip), taille déclarée par entrée et totale, taille de bloc solide
  (rejeter au-delà de ~512 Mo décompressés au scan), dictionnaire LZMA déclaré (rejeter > 64 Mo : mémoire).
- Refus : CD (cue/bin) dans une archive, comme `CD_IN_ZIP` ; mêmes règles que `analyze_zip`
  (`zip_disk_order`, 32X, `zip_disks`). Refactor : extraire un trait/enum `ArchiveReader` (listing commun
  `ArchiveEntryInfo { name, size, crc32: Option<u32>, is_file }`) pour que `analyze_zip` devienne
  `analyze_archive` sans dupliquer la logique. Table `media`/`zip_media_agrees` : étendre à `.7z`.
- Le scan ne remplit PAS de cache d'extraction (coût disque inutile).

## 3. Lancement (`emu-runtime`)

Même chemin que le zip : `media::zip_images` → `archive_images` (listing par en-tête, filtré par
`zip_entry_accepted` ; liens/dossiers/`..`/chemins absolus/noms à NUL ignorés), `workcopy` extrait vers la copie de
travail (`<work>/<hash>/`), nom de fichier = basename assaini, jamais le chemin de l'archive (zip-slip impossible).
- Archive solide : décoder séquentiellement **une seule fois** pour toutes les entrées voulues (multi-disques :
  une passe, pas N). Le CRC32 stocké est revérifié à l'écriture ; échec = erreur, copie supprimée.
- Bornes : `Limits` existant (taille par entrée, totale, `MAX_COPY_BYTES` 2 Go, ratio de compression max ~ 200:1
  vérifié en cours de flux, pas sur la taille déclarée), mémoire du dictionnaire, annulation coopérative.
- Cache : la copie de travail est déjà persistante (sauvegardes, disquettes ; `MAX_WORK_DIRS` = 64) ; pas de
  second cache. Ajouter : plafond total (défaut 1 Go, réglable) et éviction LRU des dossiers sans écritures
  utilisateur, nettoyage au démarrage des extractions inachevées (`.partial`). Disque presque plein sur le Mac :
  vérifier l'espace libre avant extraction (taille déclarée + marge 10 %), erreur claire sinon.
- Progression : `Progress { done_bytes, total_bytes, entry }` via callback `FnMut` (déjà le modèle `Limits`/
  `cancel`), affichée par l'UI (barre + bouton Annuler) car un solide LZMA2 de 200 Mo dure ~20-40 s sur le Mac ;
  l'extraction tourne hors du thread UI.

## 4. Multi-disques, CD, m3u

- Disquettes (Amiga, CPC, C64, Atari ST…) : même logique que zip (`zip_disk_order`, ≤ 32 images).
- m3u dans le 7z : ignoré comme pour zip ; m3u externe référençant un `.7z` : supporté via le même résolveur.
- CD (cue+bin, iso) dans un 7z : refusé avec le message « décompressez ou convertissez en CHD » (comme zip). Sa
  prise en charge (extraction complète en copie de travail, cue réécrit) est une extension hors 7.5.

## 5. Cores qui lisent le 7z eux-mêmes

puae, VICE (`block_extract = true`) : ADR 0017/0019 ont choisi « le frontend extrait, le core reçoit des images »
pour garder les écritures. Même règle : une archive `.7z` contenant des images acceptées est extraite par le
frontend (ordre d'évaluation du design 3.0 §3.5.1) ; sans image acceptée, transmise telle quelle si le core la lit
(`accepts_ext`) — comportement actuel conservé. Mettre à jour les lignes « `.7z` … direct » des tables 0017/0019
(pas de nouvelle ADR : renvoi vers 0023). Les cores à `block_extract = false` ne voient plus jamais un `.7z`.

## 6. Autres usages du zip

- `emu-assets/cores/archive.rs` : les cores du buildbot sont en `.zip` ; le 7z n'y est PAS ajouté (surface
  d'attaque réseau inutile). Les BIOS libres idem.
- `emu-ui/launch_firmware.rs` : `zip_entry_extensions` → lire aussi les entrées d'un `.7z` (listing d'en-tête).
  API : un seul `emu_library::archive::list_extensions(path)` pour éviter 3 implémentations.
- Placement : la lecture d'archive vit dans `emu-library` (listing + CRC) ; `emu-runtime` ne peut pas en dépendre
  (graphe) → l'extraction a sa propre dépendance `sevenz-rust2` dans `emu-runtime` (déjà le cas de `zip`) ;
  `emu-ui` appelle `emu-library`. Pas de nouveau crate, pas de changement de graphe.
