# ADR 0019 — Amstrad CPC et Commodore 64 (version 5.0) : cap32, vice_x64sc, ROM intégrées, cassettes, claviers 8 bits

Statut : proposé (2026-11-20). Réutilise ADR 0015 (infrastructure « ordinateur » de la 2.0), ADR 0017 (3.0 :
`MediaRules`, `media_direct`, import de BIOS, surcharges clavier `[remap]`, `DatSource::Libretro`) et ADR 0018 (4.0 :
`featured_options`, `reset_core_game_files`, défaut calculé depuis la langue, `.m3u` étendu) ; précise ADR 0005
(ROM système intégrées à un core), 0013 (cores) et 0014 (DAT, jaquettes). Décision utilisateur du 2026-11-20
(`docs/questions-ouvertes.md`) : **une seule version 5.0, CPC livré d'abord en pré-release, puis C64 ; repli : C64 en
5.1**. Conception détaillée : `docs/design/v5.0-cpc-c64.md`. Étude d'essais : `docs/essais-cpc-c64.md` (qa-systems).
Graphe des crates inchangé.

## Contexte

Deux ordinateurs 8 bits, sans souris ni disque dur, dont les jeux sont surtout au **joystick** et sur **cassette** ou
**disquette 3" / 5"1/4**. Ce qui change par rapport aux 2.0-4.0 :

- les ROM système (firmware, BASIC, DOS de lecteur) sont **compilées dans les cores** : rien à télécharger ni à
  importer, mais leur licence doit être examinée (ADR 0005) ;
- la **cassette** est un média à part entière : longue à charger (5 à 10 min en temps réel), pilotée par les touches
  du magnétophone (lecture, arrêt, rembobinage) que libretro n'expose pas ;
- les claviers ont des touches sans équivalent PC (CPC : COPY, CLR, pavé f0-f9 ; C64 : RUN/STOP, RESTORE, CLR/HOME,
  £, ↑, ←, C=) alors que l'utilisateur joue sur un **Razer 60 % AZERTY** (flèches, rangée F, Début/Fin/Pg↑ derrière
  Fn), touche hôte **Ctrl droit partout** (décision 2.0) ;
- le C64 a **deux ports joystick** et chaque jeu choisit le sien (1 ou 2).

## Décision

### 1. Cores

- Système `Amstrad - CPC` (`cores.toml`) : **`cap32` seul**. `crocods` écarté (pas de cassette, pas d'interface
  disque, pas de démarrage sans contenu) ; reste utilisable par `--core <chemin>`.
- Système `Commodore - 64` : **`vice_x64sc` recommandé**, **`vice_x64` en alternative** (même `.info`, mêmes
  options, VIC-II moins exact mais plus léger : repli pour le Mac Intel s'il peine, comme puae2021 en 3.0). La ligne
  de la feuille de route citait `vice_x64` : la précision de x64sc est préférée, la charge restant modeste pour un CPU
  x86_64 récent (à mesurer, design §8 ; question §9). `frodo` écarté (expérimental, sans savestate ni disque).
- Défauts frontend (`[cores.<id>] options`) :
  - `cap32` : aucun changement de défaut du core ; `cap32_lang_layout` est un **défaut calculé** (§6).
  - `vice_x64sc` / `vice_x64` : `vice_mapper_joyport_switch = "---"` (Ctrl droit est la touche hôte),
    `vice_mapper_reset = "---"` (Fin doit rester £ ; reset = Hôte + R), `vice_mapper_select = "---"` (le clavier
    virtuel est celui du frontend, comme puae), `vice_datasette_hotkeys = "enabled"` avec
    `vice_mapper_datasette_start = "RETROK_F13"`, `vice_mapper_datasette_stop = "RETROK_F14"`,
    `vice_mapper_datasette_rewind = "RETROK_F15"`, `_forward` et `_reset = "---"` (§5), `vice_autoloadwarp =
    "enabled"` (§5). Le reste garde les défauts du core.

### 2. ROM système intégrées aux cores (précision d'ADR 0005)

- **Règle générale** : une ROM système **compilée dans un binaire de core officiel du buildbot** n'est pas un
  « téléchargement de BIOS » au sens d'ADR 0005 : emu-rust télécharge le core (ADR 0013), ne l'ouvre pas, n'en
  extrait rien, ne copie aucune ROM dans `system/`, ne la redistribue pas (le binaire n'est jamais empaqueté dans les
  releases). L'état firmware affiché est **« ROM intégrées au core »** (`FirmwareState::Builtin`), avec une notice.
- **CPC** : permission explicite d'Amstrad (citée au Contexte). L'écran Cores et `THIRD-PARTY-DATA.txt` portent la
  mention exigée : « Amstrad has kindly given its permission for its copyrighted material to be redistributed but
  Amstrad retains its copyright » (ROM fournies par le core cap32 ; une partie est © Locomotive Software, CP/M
  © Digital Research).
- **C64** : **pas de permission connue** ; ROM © Commodore distribuées par l'équipe VICE depuis des décennies,
  retirées par Debian. La règle générale s'applique **sous réserve de l'accord de l'utilisateur** (question §9.1 du
  design, à poser avant le jalon C64 ; le CPC n'en dépend pas). Notice : « ROM Commodore intégrées au core VICE ;
  statut de licence incertain (© Commodore) ». Refus de l'utilisateur ⇒ le C64 sort de la 5.0 (aucun core libretro
  C64 sans ROM intégrée n'est utilisable ; Open ROMs non chargeables par vice-libretro).
- **Fichiers facultatifs de l'utilisateur** : **JiffyDOS** (commercial, toujours vendu) par « Importer un BIOS… »
  (3.0), reconnu par les md5 du `.info`, installé dans `system/vice/` (sous-dossier déclaré par le `.info`) ; après
  import du KERNAL **et** d'une ROM de lecteur, proposer `vice_jiffydos = enabled` (exige `vice_drive_true_emulation
  = enabled`, défaut). Jamais téléchargé. Aucun fichier facultatif pour le CPC en 5.0 (ROM d'extension type
  Maxam / Parados : hors périmètre).

### 3. Modèles

- **CPC** : défaut du core **6128** (128 Ko, disquette + BASIC 1.1, le plus compatible) ; les drapeaux de nom de
  fichier du core (`[464]`, `BASIC 1.0`, `[CPM]`, `[576K]`) restent actifs, le frontend ne renomme rien.
  **Cartouches `.cpr`** (CPC+ / GX4000) : défaut calculé **par extension** `cap32_model = "6128+"` (nouveau champ
  générique `options_by_extension` de `cores.toml`), sous les options globales et du jeu. Choix par jeu dans
  « Réglages CPC » (modèle, mémoire, langue, autorun, moniteur couleur / vert).
- **C64** : défaut du core **`C64 PAL auto`** (PAL, région basculée par les tags du chemin) ; NTSC, C64C, SX-64 par
  jeu dans « Réglages C64 ». Les jeux No-Intro « (USA) » ne sont pas basculés par le frontend en 5.0 (le core lit
  ses propres tags ; à vérifier en essai, design §8).

### 4. Formats et rôle du frontend

Principe 2.0 inchangé : **les fichiers de l'utilisateur ne sont jamais modifiés**.

| Système | Format | Bibliothèque | Transmis au core | Écritures |
|---|---|---|---|---|
| CPC | `.dsk` | oui (clean-cpc-db, TOSEC) | **tel quel** (`media = "direct"`) | différentiel `.sav` du core, dans un **dossier de sauvegarde par jeu** (§4.1) |
| CPC | `.cdt`, `.voc` (cassettes) | `.cdt` oui ; `.voc` sous un dossier `cpc` | tel quel | aucune |
| CPC | `.sna` (instantané) | sous un dossier `cpc` | tel quel | aucune |
| CPC | `.cpr` (cartouche CPC+ / GX4000) | oui (TOSEC) | tel quel, modèle 6128+ | aucune |
| C64 | `.d64`, `.d71`, `.d81`, `.g64`, `.nib` | oui (No-Intro pour `g64` / `nib` / `d64`, sinon nom) | **copie de travail** (`media = "working_copy"`) | dans la copie (`saves/<core>/<jeu>.disks/`) |
| C64 | `.crt` | oui (No-Intro) | copie de travail (EasyFlash réécrit la cartouche) | dans la copie |
| C64 | `.tap`, `.t64`, `.prg`, `.p00` | oui (`tap`, `prg` No-Intro) | copie de travail (un `.prg` est lancé par le système de fichiers virtuel de VICE, qui écrit à côté) | dans `<jeu>.disks/` |
| les deux | `.zip` | contenu lu sans extraction (1.0) | **extrait par le frontend** (règles 2.0 / 3.0), jamais transmis au core | selon le contenu |
| les deux | `.m3u` | oui (groupe) | `.m3u` de travail (2.0) ; lignes `#…` de l'utilisateur recopiées telles quelles (`#COMMAND:`, `#SAVEDISK:`, `#LABEL:`), suffixe `\|libellé` conservé | selon la politique |
| C64 | `.bin`, `.x64`, `.d80`, `.d82`, `.vsf`, `.cmd`, `.gz`… | non | `--rom` seulement, passé tel quel | sans garantie |

#### 4.1 Dossier de sauvegarde par jeu (générique)

- Nouveau réglage par core `save_dir = "game"` (`cores.toml`, défaut `"core"`) : `GET_SAVE_DIRECTORY` répond
  `<saves>/<core_id>/<jeu>/` au lieu de `<saves>/<core_id>/` ; SRAM et savestates du frontend inchangés (ADR 0011).
  Pour `cap32` : le `.sav` différentiel est nommé d'après le **nom de base de l'image** ; sans ce réglage, deux jeux
  dont une disquette s'appelle `DISK1.DSK` appliqueraient l'un à l'autre leurs modifications.
- « Réinitialiser les disquettes » (2.0) pour `cap32` = suppression des `*.sav` de ce dossier (motif
  `game_saves = ["*.sav"]`, `reset_core_game_files` de la 4.0 appliqué au dossier du jeu).

#### 4.2 Démarrage automatique et commande par jeu

- **Autorun / autostart du core par défaut** (cap32 : catalogue + base interne ; VICE : `LOAD"*",8,1` / cassette
  `LOAD` + `RUN`, PRG injecté). Le frontend ne tape rien lui-même.
- Option du jeu **« Commande de démarrage »** (CPC, ex. `RUN"DISC`, `|CPM`) ⇒ ligne `#COMMAND:<commande>` en tête du
  `.m3u` de travail ; **« Programme à lancer »** (C64, nom du programme sur la disquette) ⇒ première entrée
  `<image>:<programme>`. Un `.m3u` est alors généré même pour une seule image (dossier privé en `direct`,
  `<jeu>.disks/` en `working_copy`). Champ `m3u_launch = "command" | "program"` de `cores.toml` ; texte ASCII
  imprimable, ≤ 64 caractères, sans fin de ligne (et sans `:` `|` `#` pour un programme). Mémorisé dans
  `[media] launch` des options du jeu.

### 5. Cassettes : actions du frontend et chargement accéléré

- **Menu « Cassette »** (touche hôte, si le core déclare des actions) : **Lecture**, **Arrêt**, **Rembobiner**.
  Mise en œuvre générique : table `[cores.<id>.actions]` de `cores.toml` (`tape_play`, `tape_stop`, `tape_rewind` =
  nom de touche `RETROK`) ; le frontend **simule l'appui** de la touche du core pendant quelques images
  (`Emulator::pulse_key` : état clavier + événements appui / relâchement, valable pour les cores à callback comme
  cap32 et à interrogation comme VICE). cap32 : `HOME` / `END` / `PAGEUP` (raccourcis codés en dur du core) ;
  VICE : `F13` / `F14` / `F15` (configurés §1). L'OSD affiche l'action (« Cassette : lecture ») ; le compteur reste
  celui de la barre d'état du core (cap32 `cap32_statusbar`, VICE F12).
- Le menu « Disquettes » (2.0, Hôte + D) change aussi de **face** (CPC / C64 : Side A / Side B) ; les cassettes
  multiples d'un `.m3u` passent par la même interface disque (les deux cores l'acceptent).
- **Chargement accéléré** : `emu-libretro` répond à `SET_FASTFORWARDING_OVERRIDE` (64) **pour les cores marqués
  `fastforward_override = true`** (cap32, vice ; les autres reçoivent `false` comme en 3.0 / 4.0). Tant que le core
  le demande, le frontend passe en avance rapide (rythme de la demande, sinon celui de l'avance rapide 2.0), son
  coupé comme en avance rapide manuelle, OSD « Chargement accéléré » ; `inhibit_toggle` bloque la touche d'avance
  rapide de l'utilisateur. Réglage global `[computer] auto_fast_load = true` (désactivable). Pour VICE,
  `vice_autoloadwarp = enabled` (§1) déclenche la demande pendant les accès disque et cassette.

### 6. Claviers sur Razer 60 % AZERTY

- Correspondance **positionnelle** de la 2.0 (touche physique ⇒ `RETROK_*` US), puis **surcharges** `[remap]` du
  clavier de chaque système (`data/keyboards/{cpc,c64}.toml`, mécanisme 3.0), modifiables par
  `[computer.remap.<système>]`. Ctrl droit (touche hôte) n'atteint jamais le core.
- **Disposition CPC** : défaut calculé depuis la langue du système, comme `dosbox_pure_keyboard_layout` (4.0), mais
  déclaré en données : `layout_option = { option = "cap32_lang_layout", map = { fr = "french", es = "spanish" },
  fallback = "english" }` ⇒ un AZERTY obtient le **CPC français** (ROM et clavier AZERTY d'origine), les légendes
  correspondent. Le C64 reste en disposition positionnelle US (pas de C64 AZERTY ; `vice_keyboard_keymap =
  positional`).
- **CPC** (cap32) :

  | Touche CPC | `RETROK` lu par cap32 | Razer 60 % (Windows / Linux) | macOS |
  |---|---|---|---|
  | COPY | `LALT` / `RALT` | **Alt gauche** ou **AltGr** | ⌥ |
  | CLR | `DELETE` | Suppr (Fn) ou clavier virtuel | Fn + ⌫ |
  | DEL | `BACKSPACE` | ⌫ | ⌫ |
  | CONTROL | `LCTRL` | Ctrl gauche | Ctrl |
  | f1…f9, f0 (pavé) | `KP1`…`KP9`, `KP0` | **surcharge : F1…F9, F10** (Fn + rangée des chiffres) | idem |
  | f. et ENTER du pavé | `KP_PERIOD`, `KP_ENTER` | **surcharge : F11, F12** | idem |
  | Curseurs | flèches | flèches (Fn) ; mode Joystick | idem |

  La surcharge F1-F12 a un second effet voulu : `F9` / `F10` (menu et clavier virtuel **du core**) ne lui
  parviennent plus. `Début` / `Fin` / `Pg↑` (Fn) restent les touches cassette du core (sans équivalent CPC) ;
  `Inser` (bascule curseurs ⇄ joystick du core) aussi, documentée.
- **C64** (VICE, table positionnelle du core + surcharges) :

  | Touche C64 | `RETROK` lu par VICE | Razer 60 % (Windows / Linux) | macOS |
  |---|---|---|---|
  | RUN/STOP | `ESCAPE` | **Échap** | Échap |
  | RESTORE | `PAGEUP` | **surcharge : Alt droit / AltGr** (et Pg↑ par Fn) | ⌥ droit |
  | C= (Commodore) | `LCTRL` | **Ctrl gauche** | Ctrl |
  | CTRL | `TAB` | Tab | Tab |
  | CLR/HOME | `HOME` | Début (Fn) ou clavier virtuel | Fn + ← |
  | INST/DEL | `BACKSPACE` (Maj = INST), `INSERT` | ⌫ | ⌫ |
  | £ | `END` | **surcharge : `<`** (`IntlBackslash`, touche ISO absente du C64 US) ; Fin (Fn) | `IntlBackslash` |
  | ↑ (flèche haute de la rangée) | `BACKSLASH` | touche `*` à gauche d'Entrée (position ISO de `\`) | idem |
  | ← (en haut à gauche) | `BACKQUOTE` | `²` si présente sur le modèle, sinon clavier virtuel | `@` / `<` selon le clavier |
  | F1-F8 | `F1`…`F8` | Fn + rangée des chiffres | idem |
  | Curseurs | flèches | flèches (Fn) ; mode Joystick | idem |

- **Claviers virtuels** (Hôte + K) : `cpc.toml` (CPC 6128 : pavé f0-f9, COPY, CLR, ENTER ; légendes `english`,
  `french`, `spanish` selon `cap32_lang_layout`) et `c64.toml` (C64 : RUN/STOP, RESTORE, CLR/HOME, INST/DEL, £, ↑, ←,
  C=, F1-F8 en colonne ; légendes `us`).
- **Mode d'entrée** : celui de la 2.0, **Clavier** par défaut (décision utilisateur 2.0, appliquée ici sans autre
  décision), Hôte + J pour le mode Joystick (ZQSD + J / K = RetroPad port 0), **mémorisé par jeu**. La 5.0 pose la
  question d'un défaut *Joystick* pour ces deux systèmes (design §9). Entrées « BASIC » sans contenu : toujours
  Clavier.

### 7. Joystick

- **CPC** : RetroPad port 0 = joystick 1 (`cap32_retrojoy0 = auto` : la base interne du core peut associer les
  boutons à des touches selon le jeu) ; port 1 = joystick 2. Rien de propre au frontend.
- **C64** : RetroPad port 0 = **port C64 choisi par `vice_joyport`** (défaut `2`). Menu de la touche hôte **« Port
  joystick : 1 ⇄ 2 »** : change l'option (appliquée à chaud par le core) et l'enregistre dans les options du jeu ;
  OSD « Joystick sur le port 1 ». Les tags `(j1)` / `(j2)` du nom de fichier restent prioritaires (le core ignore
  alors l'option jusqu'au redémarrage : le menu l'indique). Deux manettes (phase 6) : port 1 libretro = l'autre
  port C64.

### 8. Options par jeu

- Mécanisme 2.0 + `featured_options` (4.0) : **« Réglages CPC »** = `cap32_model`, `cap32_ram`, `cap32_lang_layout`,
  `cap32_autorun`, `cap32_retrojoy0`, `cap32_tape_fastload`, `cap32_scr_tube` ; **« Réglages C64 »** =
  `vice_c64_model`, `vice_joyport`, `vice_sid_model`, `vice_autostart`, `vice_drive_true_emulation`,
  `vice_autoloadwarp`, `vice_jiffydos`. Plus « Commande de démarrage » / « Programme à lancer » (§4.2).
- Ordre de priorité inchangé : défauts du core < `cores.toml` < défauts calculés (langue, extension) < config <
  jeu.

### 9. Bibliothèque et identification

- Systèmes `id = "cpc"` (`database = "Amstrad - CPC"`, `dat = ["libretro", "tosec"]` : clean-cpc-db puis TOSEC,
  ScreenScraper 65 et IGDB 25 **à vérifier**) et `id = "c64"` (`database = "Commodore - 64"`, `dat = ["no-intro"]`,
  ScreenScraper 66 et IGDB 15 **à vérifier**), `kind = "computer"`.
- Extensions : CPC `dsk`, `cdt`, `cpr`, `m3u` partout ; `sna`, `voc` seulement sous un dossier `cpc` (ambiguës :
  ZX Spectrum, audio). C64 `d64`, `d71`, `d81`, `g64`, `nib`, `t64`, `tap`, `prg`, `p00`, `crt`, `m3u` ; `bin`
  exclu (ambigu). Zips : système déduit des entrées (1.0) ; `.dsk` dans un zip = CPC.
- Groupes multi-disques / faces : règles 2.0 (`(Disk N of M)`, `(Side A)` / `(Side B)`), plus `(Tape N of M)`.
- Identification : CRC32 puis SHA-1 contre chaque DAT dans l'ordre (3.0) ; **les dumps C64 courants (`.d64` des
  collections) ne sont pas dans No-Intro** : repli sur le nom (règle 1.0), jaquette par titre normalisé. Pas de DAT
  TOSEC C64 : il n'est pas dans libretro-database et le site TOSEC ne fournit pas d'URL stable (écarté comme en 4.0).
- Jaquettes : libretro-thumbnails `Amstrad_-_CPC`, `Commodore_-_64` (titres du DAT), puis ScreenScraper / IGDB (1.0).
- Entrées **« Amstrad CPC (BASIC) »** et **« Commodore 64 (BASIC) »** (démarrage sans contenu, comme « Bureau Atari
  ST ») : les deux cores ont `supports_no_game`.

### 10. Écarts avec la 2.0, la 3.0 et la 4.0

| Sujet | 2.0 ST / 3.0 Amiga / 4.0 DOS | 5.0 CPC / C64 |
|---|---|---|
| ROM système | EmuTOS téléchargé ; Kickstart importé (AROS en repli) ; aucune (DOS) | **intégrées au core** (`Builtin`) ; JiffyDOS importé facultatif |
| Médias | disquettes / disque dur / zip-dossier | **+ cassettes** (menu Cassette, chargement accéléré), cartouches |
| Écritures | copies de travail ; `.pure.zip` du core | CPC : **différentiel du core**, dossier de sauvegarde **par jeu** ; C64 : copies de travail |
| Lancement | boot / menu du core | autorun du core + **commande ou programme par jeu** (`.m3u`) |
| Clavier | positionnel + surcharges ; langue de TOS / DOS | idem ; langue du CPC calculée ; surcharges F1-F12 ⇒ pavé (CPC), AltGr ⇒ RESTORE, `<` ⇒ £ (C64) |
| Joystick | port 0 | C64 : **port 1 / 2 par jeu** |
| FFI | 12, 13, 57, 58 ; VFS v3 opt-in | **+ 64 `SET_FASTFORWARDING_OVERRIDE` opt-in** |
| Bibliothèque | TOSEC, WHDLoad, `DOS.dat` | clean-cpc-db + TOSEC (CPC), No-Intro (C64) |

## Conséquences

- Nouvelles API (détail : design §3) : `emu_libretro::{CoreConfig::fastforward_override, FastForwardOverride,
  RunEvents::fastforward}` ; `emu_runtime::{Emulator::pulse_key, Emulator::fastforward_override, SaveScope,
  EmulatorOptions::core_save_scope, MediaSet::launch, MediaRules::m3u_launch, M3uLaunch}` ; `emu_assets` :
  `CorePreferences::{save_scope, fastforward_override, options_by_extension, m3u_launch, actions, builtin_firmware,
  layout_option}`, `FirmwareState::Builtin` ; `emu_library` : systèmes `cpc` / `c64`, `(Tape N of M)`.
  Graphe inchangé, **aucune nouvelle dépendance**.
- `unsafe` nouveau : la lecture de `retro_fastforwarding_override` dans le callback d'environnement (revue
  `reviewer`). Réseau nouveau : aucun hôte nouveau (cores du buildbot, DAT de libretro-database).
- Les mécanismes génériques (dossier de sauvegarde par jeu, actions de core par touches simulées, options par
  extension, avance rapide demandée par le core, disposition calculée en données) servent ensuite à d'autres cores
  (ZX Spectrum, MSX, puae pour WHDLoad). Le défaut calculé de `dosbox_pure_keyboard_layout` (4.0) pourra migrer vers
  `layout_option` sans changement visible.
- Le C64 dépend d'une décision de l'utilisateur sur les ROM intégrées (§2) ; le jalon CPC n'en dépend pas.
- Les cores sont des nightlies : raccourcis codés en dur de cap32 et noms d'options VICE peuvent changer ; les tests
  `#[ignore]` sur cores réels et les empreintes le détectent (version précédente conservée, ADR 0013).
